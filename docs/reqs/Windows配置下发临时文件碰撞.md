## 需求背景

### 业务背景

BSCP 向 Windows 主机下发配置时，由 `ScriptBuilder` 生成一段 `.bat` 脚本交给 GSE 执行。脚本把配置内容以 base64 形式内联，落到临时文件后用 `certutil -decode` 还原，再 `move` 到目标路径。

2026-08-21 的正式环境配置下发批次（batch_id 2360，8 个任务）出现大面积失败：首轮 8 个任务失败 4 个，重试后失败 2 个，再次重试才全部成功。失败集中在 Windows 目标机，且报错不稳定、重试可缓解，是典型的并发竞态特征。

### 现场证据

批次 2360 的 8 个任务分布在两台 Windows 主机上，每台主机内都存在多个任务下发**同名**配置文件（目录不同）：

| 主机 IP | Agent ID | 任务数 | 同名文件 |
|---------|----------|--------|---------|
| 11.152.235.253 | 02000000005254000fbd261703648156988d | 3 | 3 个 `Web.config`（Trade-web / Trade-game / Trade-process） |
| 11.152.235.188 | 02000000005254007a01141703648144112b | 5 | 3 个 `Web.config`（Ingame-cn-api / idip-api / Ingame-contents） |

`.188` 上另有 2 个 Oasis 任务，与上述任务**同主机、同目录、同进程（cc_process_id 20247631）**，唯一区别是文件名不同（`BlackDesertLog.xml` / `BlackDesertWorld.xml`）——这 2 个任务三轮均未失败，构成天然对照组，把变量精确锁定在「文件名」而非主机、权限或并发本身。

三轮执行（`task_step_records.ReleaseConfig` 的 start 时间）的失败分布：

| 轮次 | 时间 | 成功 | 失败 |
|------|------|------|------|
| 第 1 轮 | 05:35:08 | 4（含 2 个 Oasis 对照组） | 4（`.253` 全部 3 个 + `.188` 的 Ingame-cn-api） |
| 第 2 轮 | 06:28:36 | 2（分属不同主机，物理上不可能碰撞） | 2（均在 `.253`） |
| 第 3 轮 | 06:29:29 | 2 | 0 |

两种失败报文（同一 agent、同一批次）：

```text
# 报文 A
[INFO] 目标文件不存在，跳过备份。
Input Length = 8191
EncodeToFile returned The file exists. 0x80070050 (WIN32: 80 ERROR_FILE_EXISTS)
CertUtil: -decode command FAILED: 0x80070050 (WIN32: 80 ERROR_FILE_EXISTS)

# 报文 B
[INFO] 目标文件不存在，跳过备份。
Input Length = 8191
Output Length = 6143
CertUtil: -decode command completed successfully.
The system cannot find the file specified.

```

两条报文都显示备份步骤被正常跳过（目标文件首次下发不存在），说明失败与备份逻辑无关，原单据名「备份配置失败」不准确。

### 根因分析

脚本中临时文件的命名为：

```bat
set "BSCP_TMP=%TEMP%\bscp_!TARGET_NAME!_%RANDOM%.b64"
set "BSCP_OUT=%TEMP%\bscp_!TARGET_NAME!_%RANDOM%.out"
```

唯一性只依赖两个因素，两个都不可靠：

1. **`TARGET_NAME` 只取文件名、不含目录**。同一主机上若干 .NET 服务各有一份 `Web.config`，只是目录不同，它们会挤进同一个命名空间。
2. **`%RANDOM%` 由 cmd 进程启动时的系统时钟播种**。GSE 在同一瞬间拉起的多个 cmd.exe 会得到完全相同的随机序列，算出完全相同的临时文件名。

两个因素叠加后产生如下竞态（A、B 为同主机上并发的两个下发任务）：

| 时刻 | 任务 A | 任务 B |
|------|--------|--------|
| 1 | `certutil` 解码成功，创建 `.out` | |
| 2 | | `certutil` 解码，`.out` 已存在 → `ERROR_FILE_EXISTS`（`certutil -decode` 未带 `-f`，默认拒绝覆盖） |
| 3 | | 进入失败分支执行 `del "!BSCP_OUT!"`，**删掉的是 A 的产物** |
| 4 | `move` 找不到 `.out` → `MOVE_FAILED` | |

报文 A 来自任务 B，报文 B 来自任务 A，二者是同一场竞态的两半。`.253` 首轮 3 个任务全部失败，与 3 个 cmd 取到同一 `%RANDOM%` 的推断一致；失败率随并发对数下降（4 → 2 → 0）而非随重试次数下降，进一步排除了「残留文件」等非并发解释。

### 次生风险

除了可见的下发失败，同一命名空间还带来两个不报错的隐患：

- **配置内容串号**：多个任务共用同一个 `.b64` 中转文件，后写的 `echo` 会覆盖先写的，先执行的 `certutil` 会解码出**其他任务的配置内容**并写入自己的目标路径，全程无任何报错。批次 2360 中同一碰撞组内各任务的 `ConfigContentSignature` 互不相同，该风险真实存在。
- **非原子替换**：`%TEMP%` 通常在 C 盘而目标在 D 盘，跨卷 `move` 退化为「拷贝 + 删除」，业务进程有机会读到只写了一半的配置文件。Linux 侧脚本已刻意将临时文件置于目标同目录以保证 `rename` 原子性，Windows 侧未对齐。

此外，`mkdir` 失败未做拦截，错误会一路滑到 `move` 才暴露，报成语义完全不同的「找不到文件」，显著增加定位成本。

### 用户故事

作为 BSCP 的配置管理员
我想要向同一台 Windows 主机并发下发多个同名配置文件时，各任务互不干扰
以便于批量发布一次成功，不必靠反复重试碰运气

作为业务方运维
我想要下发「成功」的配置文件内容一定是本任务自己的内容
以便于不会因为静默串号而把错误配置带到线上

## 功能需求

### 核心功能点

| 功能编号 | 功能描述 | 优先级 | 涉及角色 | 备注 |
|---------|---------|--------|---------|------|
| F-001 | 临时文件名后缀改由服务端生成全局唯一值，不再使用 cmd `%RANDOM%` | P0 | 后端 | 必须 |
| F-002 | 临时文件从 `%TEMP%` 迁移到目标文件同目录 | P0 | 后端 | 必须 |
| F-003 | `certutil -decode` 增加 `-f` 强制覆盖参数 | P0 | 后端 | 必须 |
| F-004 | 解码前按精确文件名清理同名残留 | P1 | 后端 | 应该有 |
| F-005 | `mkdir` 失败时立即终止并输出可识别错误标识 | P1 | 后端 | 应该有 |

### 详细功能描述

#### [F-001] 服务端生成唯一临时文件后缀

- **输入**：`buildWindowsPushScript` 构建一次下发脚本
- **处理逻辑**：
  1. 在 Go 侧生成一个全局唯一的随机后缀（不少于 64 位熵）
  2. 将该后缀作为常量嵌入生成的 `.bat` 脚本
  3. 脚本内不再出现 `%RANDOM%`
- **输出**：脚本中 `BSCP_TMP` / `BSCP_OUT` 携带唯一后缀
- **边界条件**：同一目标路径的重复构建（重试、并发下发同一配置）也必须得到不同后缀
- **异常处理**：随机源不可用 → 退化为纳秒时间戳，不得抛错中断下发

#### [F-002] 临时文件与目标同目录

- **输入**：目标绝对路径 `TARGET_PATH`
- **处理逻辑**：
  1. 由 `TARGET_DIR` + `TARGET_NAME` + 唯一后缀拼出临时文件路径
  2. `move` 的源与目的位于同一目录，落到同卷内的原子 rename
- **输出**：`%TEMP%` 不再参与下发链路
- **边界条件**：临时文件命名不得与备份文件通配规则 `<文件名>.*.bak` 相交，避免被备份清理逻辑误删
- **异常处理**：目标目录不可写 → 由 F-005 在建目录阶段拦截

#### [F-003] certutil 强制覆盖

- **输入**：base64 中转文件、解码输出路径
- **处理逻辑**：执行 `certutil -f -decode`
- **输出**：输出文件已存在时正常覆盖，不再返回 `0x80070050`
- **异常处理**：非「文件已存在」类失败仍走 `DECODE_FAILED` 分支并退出码 1

#### [F-004] 解码前清理同名残留

- **输入**：本次生成的 `BSCP_TMP` / `BSCP_OUT` 路径
- **处理逻辑**：按**精确文件名**删除，删除失败静默忽略
- **输出**：解码在干净状态下开始
- **边界条件**：**禁止**使用 `<文件名>.bscp.*` 之类的通配清理——那会删掉并发任务正在使用的临时文件，等价于把本次缺陷换个形式放回来
- **异常处理**：文件被占用导致删除失败 → 由 F-003 的 `-f` 兜底

#### [F-005] 建目录失败即终止

- **输入**：`TARGET_DIR`
- **处理逻辑**：`mkdir` 后复查目录是否存在，不存在则输出 `MKDIR_FAILED` 并 `exit /b 1`
- **输出**：错误在建目录阶段暴露，不再滑到 `move`
- **异常处理**：目录已存在时不重复创建，不报错

## 非功能需求

### 性能需求

- 单次下发脚本执行耗时不劣化：改动不引入额外进程调用，`del` 与目录检查的开销可忽略（相对当前约 2 秒的单任务执行时长，增量应 < 100ms）。

### 安全需求

- 临时文件落在目标目录内，继承目标目录的既有 ACL；下发完成后不得残留 `.b64` 中转文件（其中含配置明文的 base64）。
- 属主与权限设置（`icacls`）作用于最终目标文件的行为保持不变。

## 验收标准

### 功能验收

- [ ] **AC-001**：Given 同一台 Windows 主机上有 N（N≥3）个任务并发下发**同名但不同目录**的配置文件，When 一次性触发批量下发，Then 全部任务一次成功，不出现 `DECODE_FAILED` 或 `MOVE_FAILED`。
- [ ] **AC-002**：Given 上述并发下发场景，When 全部任务执行完成，Then 每个目标文件的 MD5 与 `config_instances.md5` 中对应记录一致，不存在内容串号。
- [ ] **AC-003**：Given 对同一目标路径连续构建两次下发脚本，When 比对两份脚本，Then `BSCP_TMP` 与 `BSCP_OUT` 的取值互不相同，且脚本中不含 `%RANDOM%` 与 `%TEMP%`。
- [ ] **AC-004**：Given 解码输出文件已存在于目标目录，When 执行下发脚本，Then `certutil` 正常覆盖并完成下发，不再返回 `0x80070050 ERROR_FILE_EXISTS`。
- [ ] **AC-005**：Given 目标目录因权限或磁盘原因无法创建，When 执行下发脚本，Then 脚本在建目录阶段输出 `MKDIR_FAILED` 并以退出码 1 结束，不产生 `MOVE_FAILED` 报文。
- [ ] **AC-006**：Given 目标文件已存在且历史备份数达到上限，When 执行下发，Then 备份轮转行为不变，且临时文件不被计入备份数量、不被备份清理逻辑删除。
- [ ] **AC-007**：Given Linux 目标机，When 执行配置下发，Then 行为与改动前完全一致（无回归）。

### 性能验收

- [ ] **AC-P01**：单任务 `ReleaseConfig` 步骤执行耗时相对改动前增量 < 100ms（对比基准：批次 2360 的 2023–2054ms）。
