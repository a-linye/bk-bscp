## 需求背景

### 业务背景

**当前业务问题**：bscp 承接 gsekit 的进程操作能力后，存量业务从 gsekit 迁移到 bscp，出现进程启动失败。经源码核对（见 `docs/process-operate-priority-gsekit-vs-bscp.md`），根因是 **bscp 未承接 gsekit 的启动优先级编排能力**：

- CMDB 进程对象存在 `priority`（启动优先级）字段，业务已在 CMDB 上完成配置
- gsekit 后台读取该字段，用 Bamboo Pipeline 按优先级分批串行执行，保证「低优先级先起、高优先级后起」
- GSE **不感知** priority（`operate_proc_multi` 请求体无该字段），顺序完全由调用方决定分几次调用、按什么顺序调用
- bscp 的 CMDB 客户端虽能解析 `priority`（`internal/components/bkcmdb/type.go`），但同步落库时被丢弃；`OperateProcess` 按进程实例逐条 `Dispatch` 到 200 worker 的全局并发池，**无任何顺序保证**

**后果**：业务在 CMDB 上配置的启动优先级对 bscp 完全失效。凡是存在启动依赖关系的进程组（如「先起数据库代理，再起应用进程」），迁移到 bscp 后依赖方会在被依赖方尚未就绪时启动，导致启动失败。

**目标用户**：从 gsekit 迁移到 bscp 进程管理的存量业务运维人员（在 CMDB 上已配置 `priority` 的业务）。

**使用场景**：在 bscp 进程管理页选择一批进程/进程实例（或用操作范围表达式圈定范围），执行启动、停止、重启等操作。

**不做的影响**：存量 gsekit 用户无法迁移到 bscp；已迁移业务持续出现顺序类启动失败，需人工按优先级分批手动操作。

### 业务目标（量化）

| 指标 | 现状 | 目标 |
|------|------|------|
| CMDB 已配 `priority` 业务的启停顺序正确率 | 无顺序保证（0%） | 与 gsekit 一致：批次划分与执行顺序 100% 一致 |
| 顺序类启动失败工单 | 存在（迁移用户投诉） | **降为 0** |
| 优先级编排的用户可感知性 | 任务详情无优先级信息 | 任务详情可见每个实例的优先级，失败原因可定位到「因前序优先级失败而未执行」 |

### 用户故事

**US-1（优先级数据可用）**
作为 从 gsekit 迁移的业务运维人员
我想要 我在 CMDB 上配置的进程启动优先级被 bscp 读取并生效
以便于 不需要为了迁移而重新在另一个系统里维护一份优先级配置

**US-2（启动按升序）**
作为 存在启动依赖关系的业务运维人员
我想要 执行「启动」时，优先级小的进程先启动完成，再启动优先级大的进程
以便于 被依赖的进程先就绪，依赖方不再因为对端未启动而失败

**US-3（停止/重启按降序）**
作为 需要安全下线的业务运维人员
我想要 执行「停止」和「重启」时，优先级大的进程先被停止
以便于 上层依赖方先退出，避免被依赖进程先消失导致上层报错刷屏

**US-4（失败即止）**
作为 批量操作的业务运维人员
我想要 某个优先级批次没有全部成功时，后续优先级的进程不再被执行
以便于 依赖链断裂时立即止损，而不是在错误的前提下继续操作后面几百个实例

**US-5（失败可定位）**
作为 排查操作失败的业务运维人员
我想要 在任务详情里看到每个实例的优先级，以及「因前序优先级失败而未执行」这类明确原因
以便于 一眼分清「进程本身操作失败」和「被前序失败连带阻断」，只重点排查真正的失败源

**US-6（重试保持顺序）**
作为 处理完失败原因后重试的业务运维人员
我想要 重试同样按优先级分批串行执行
以便于 重试不会退化成无序并发，重试结果和首次执行具有相同的顺序保证

**US-7（托管类不受影响）**
作为 执行托管/取消托管的业务运维人员
我想要 托管类操作不因优先级被拆成多批串行
以便于 托管类操作不涉及启停依赖，不必为此付出串行等待的时间代价

### 详细功能描述

#### [F-001] 从 CMDB 同步并持久化进程启动优先级

- **输入**：CMDB 进程属性中的 `priority`（启动优先级），随现有 CMDB 定时同步（默认 30 分钟一轮、每轮 10 个业务）或用户在 UI 手动触发同步获取
- **处理逻辑**：
  1. 现有 CMDB 同步链路解析进程属性时，保留 `priority` 值
  2. 将 `priority` 与进程记录一并持久化到 bscp 侧，使其可用于操作编排与任务详情展示
  3. `priority` 缺失、为空或为 `null` 时，按 **0** 处理
- **输出**：bscp 侧每个进程具备可查询的启动优先级
- **边界条件**：
  - `priority` 为整型，可为负数（负数视为比 0 更早启动）
  - CMDB 上修改 `priority` 后，最长需等待一轮定时同步（默认 30 分钟）生效；用户可手动触发同步立即生效
- **异常处理**：
  - CMDB 同步失败 → 沿用上一次同步值，不因缺少 priority 阻断进程操作
  - CMDB 返回非整型 priority → 按 0 处理，并记录日志

#### [F-002] 按操作类型排序并分批

- **输入**：一次进程操作请求（`OperateProcess`），包含操作类型与待操作的进程实例集合（可来自进程 ID 列表、进程实例 ID 列表或操作范围表达式三种入口）
- **处理逻辑**：
  1. 解析出本次待操作的全部进程实例
  2. 取每个实例所属进程的 `priority`
  3. 按操作类型确定排序方向（见业务规则 R-002）
  4. 按 `priority` 分组：同一 `priority` 的所有实例归为一批
  5. 批次之间按排序方向依次执行
- **输出**：一个按优先级有序的批次序列
- **边界条件**：
  - 全部实例 `priority` 相同 → 只有一批，等价于现有并行行为，不引入串行等待
  - 单个实例 → 一批
  - 三种操作入口（进程 ID / 进程实例 ID / 操作范围表达式）均适用同一编排规则
- **异常处理**：
  - 待操作实例集合为空 → 沿用现有校验，不创建批次

#### [F-003] 批次串行门控

- **输入**：F-002 产出的有序批次序列
- **处理逻辑**：
  1. 下发当前批次内全部实例任务，批次内并行执行
  2. 等待本批次全部实例任务到达终态
  3. 本批次全部实例任务终态为成功 → 下发下一批次
  4. 本批次存在非成功终态 → 转 F-004
  5. 重复至批次序列耗尽
- **输出**：批次按序执行；批次统计与终态沿用现有任务批次机制（`running` → `succeed` / `failed` / `partly_failed`）
- **边界条件**：
  - 单个实例任务的成功判定沿用现有实例任务内部步骤（其中已含 GSE 进程状态校验与收尾），**不新增独立的批次级 GSE 状态复查环节**
  - 单批次内不额外限制并发规模，沉降到现有 200 worker 全局并发池自然限流
- **异常处理**：
  - 实例任务长时间不结束（如 Agent 失联）→ 沿用现有任务步骤级超时（默认 3 分钟）判定为超时，超时视为非成功，转 F-004；**不引入独立的批次级超时**

#### [F-004] 失败级联阻断

- **输入**：某一批次出现非成功终态（失败或超时）
- **处理逻辑**：
  1. 不再下发后续优先级的批次
  2. 将后续所有优先级中尚未执行的实例任务置为失败
  3. 为这些任务写入明确的失败原因，文案对齐 gsekit 语义（区分升序 / 降序两种表述）
  4. 本批次内已在执行中的任务不打断，让其自然结束；已成功的任务保留成功
- **输出**：任务详情中，被阻断的任务显示为失败，失败原因指明「因优先级 X 的进程操作失败，本任务不会被继续执行」
- **边界条件**：
  - 被级联阻断的任务计入批次的失败计数
  - 阻断范围为本次操作请求内（单业务）的后续全部优先级
- **异常处理**：
  - 批次内既有成功又有失败 → 后续批次仍被阻断（判定标准为「非全部成功即阻断」，不设失败率阈值）

#### [F-005] 托管类操作退化为单批

- **输入**：操作类型为 register（托管）、unregister（取消托管）、update_register（更新托管配置）
- **处理逻辑**：忽略实例的实际 `priority` 差异，将全部实例归为同一批并行执行
- **输出**：托管类操作无跨优先级串行等待，行为与现状一致
- **边界条件**：即使实例间 `priority` 取值不同，也不拆分批次
- **异常处理**：沿用现有托管类操作的失败处理，不产生跨优先级级联

#### [F-006] delete 语义拆解后的优先级行为

- **输入**：操作类型为 delete
- **处理逻辑**：delete 依据实例状态与托管状态拆解为三类分支，各分支的优先级行为分别为：
  1. **stop 分支** → 按 `priority` **降序**分批串行（与 stop 语义一致）
  2. **unregister 分支** → 同一批并行，不分优先级（与托管类语义一致）
  3. **直接删库分支** → 不下发任务，不参与优先级编排
- **输出**：delete 的顺序行为与其拆解出的子操作语义保持一致
- **边界条件**：一次 delete 请求可能同时命中三类分支
- **异常处理**：stop 分支失败时，级联规则同 F-004

#### [F-007] 失败重试按优先级重新编排

- **输入**：用户对某个任务批次执行失败重试
- **处理逻辑**：
  1. 收集该批次的失败任务集合，**包含被 F-004 级联阻断的任务**
  2. 对该集合按 F-002 规则重新排序分批
  3. 按 F-003 / F-004 规则串行执行并门控
- **输出**：重试执行具备与首次执行相同的顺序保证
- **边界条件**：重试集合中若只剩单一优先级 → 单批并行
- **异常处理**：重试过程中再次出现批次失败 → 同样触发级联阻断

#### [F-008] 任务详情展示进程优先级

- **输入**：用户查看任务批次详情
- **处理逻辑**：任务详情接口返回每个实例任务对应进程的 `priority`；前端在实例维度表格中新增「进程优先级」列
- **输出**：任务详情表格可见每行实例的优先级
- **边界条件**：
  - 优先级取值为 0 时显示 `0`（不显示为空）
  - 优先级缺失/不可取得时显示 `--`
  - 保持现有扁平实例列表形态，**不做按优先级分组折叠或分阶段进度条**
- **异常处理**：优先级字段取不到 → 显示 `--`，不影响表格其余内容渲染

## 非功能需求

### 性能需求

> 说明：用户确认「对齐 gsekit 即可」，未给出独立数字要求。以下指标由 gsekit 现网行为参数推导得出，属假设，见「假设与未决问题」A-4。

- **批次切换开销**：跨优先级批次切换引入的额外等待（从本批最后一个任务到达终态，到下一批首个任务开始执行）**≤ 5 秒**
  - 测量场景：单业务 2000 个进程实例、10 个不同 `priority` 取值、执行 start
  - 测量方式：对比 `task_records` 中相邻批次的任务时间戳（前批最大结束时间 vs 后批最小开始时间）
- **单批并发**：同一优先级批次内不额外限制并发，沉降到现有 200 worker 全局并发池
  - 测量场景：单批 2000 个实例
  - 测量方式：观测同时处于 `running` 的实例任务数 ≤ 200，且 GSE 调用 QPS 不高于改造前基线
- **规模能力**：单次操作 ≤ 5000 个进程实例、≤ 20 个不同 `priority` 取值时功能正常
  - 测量场景：构造 5000 实例 / 20 个优先级取值的 start 操作
  - 测量方式：批次数等于优先级取值数，全部批次按序执行完成，无任务丢失（`task_batches.total_count` 与实际实例数一致）

### 安全需求

- **权限控制**：沿用现有 `OperateProcess` 的 IAM 鉴权，本需求**不新增**权限点，不放宽任何现有校验
  - 测量方式：无进程操作权限的用户调用 `/process/operate`，返回鉴权失败，与改造前一致
- **数据保护**：`priority` 非敏感数据，无加密/脱敏要求
- **合规要求**：无新增

### 可用性与稳定性

- **向后兼容**：所有实例 `priority` 相同（含全为 0 的未配置业务）时，执行路径退化为单批并行，行为与改造前一致
  - 测量方式：未配置 priority 的业务执行 start，批次数为 1，任务下发形态与改造前一致
- **容错能力**：
  - CMDB 同步不可用时，使用上一次同步的 priority 值，进程操作不被阻断
  - 优先级信息缺失时按 0 处理，退化为单批并行，不返回错误

### 兼容性

- **接口兼容**：`OperateProcess` 请求/响应结构**不新增字段**，调用方无需改造；任务详情查询接口在响应中新增优先级字段，属向后兼容的字段新增
- **数据兼容**：改造前已存在的历史任务批次记录无优先级信息，任务详情中该列显示 `--`

## 业务规则

### 业务逻辑规则

- **规则 R-001（优先级数据来源与默认值）**：`priority` 唯一数据源为 CMDB，bscp 侧**只读**，不提供编辑入口，用户修改优先级仍在 CMDB 操作。`priority` 缺失、为空或为 `null` 时按 **0** 处理。
- **规则 R-002（排序方向）**：按操作类型确定优先级排序方向，与 gsekit 严格一致：

| 操作类型 | 排序方向 | 语义 |
|---------|---------|------|
| start（启动） | **升序**（小 → 大） | 先启动低优先级 |
| reload（重载） | **升序** | 先重载低优先级 |
| kill（强制停止） | **升序** | 先强杀低优先级 |
| stop（停止） | **降序**（大 → 小） | 先停止高优先级 |
| restart（重启） | **降序** | 先重启高优先级 |
| register（托管） | 不分优先级 | 单批并行 |
| unregister（取消托管） | 不分优先级 | 单批并行 |
| update_register（更新托管配置） | 不分优先级 | 单批并行 |
| delete（删除） | 依拆解分支而定 | 见 R-007 |

- **规则 R-003（托管类强制单批）**：register / unregister / update_register 三类操作不参与优先级分批，无论实例 `priority` 是否不同，均归为一批并行。
- **规则 R-004（分批串行）**：同一 `priority` 的实例归为一批、批内并行；不同 `priority` 的批次之间串行，**前一批全部实例任务成功后才下发下一批**。
- **规则 R-005（失败门控）**：本批次存在任一非成功终态（失败或超时）时，后续所有优先级的**尚未执行**任务置为失败，并写入指明前序优先级失败的原因文案；本批已在执行中的任务不打断，已成功的保留成功。判定标准为「非全部成功即阻断」，不设失败率阈值。
- **规则 R-006（编排范围）**：优先级串行链的生效范围为**一次操作请求内**。由于 bscp 一次 `OperateProcess` 请求本身限定单个业务，等价于 gsekit 默认的业务（BIZ）聚合粒度：同一次操作内跨集群、跨模块、跨主机的实例共用**一条**串行链。本期不提供聚合粒度配置能力。
- **规则 R-007（delete 拆解）**：delete 拆解出的 stop 分支按 `priority` 降序分批串行；unregister 分支单批并行；直接删库分支不参与编排。
- **规则 R-008（重试语义）**：失败重试对失败任务集合（含被级联阻断的任务）按 R-002 ~ R-005 重新完整编排一次。
- **规则 R-009（超时处理）**：不引入独立的批次级超时，依赖现有任务步骤级超时（默认 3 分钟）判定实例任务为超时；超时视为非成功终态，触发 R-005。

### 数据校验规则

- **必填字段**：无新增必填字段（`OperateProcess` 请求不变）
- **格式要求**：`priority` 为整型
- **取值范围**：不限制上下界（与 gsekit 一致，CMDB 侧亦无范围校验）；缺省值 0

### 权限规则

沿用现有进程操作权限模型，不新增角色与权限点。

## 验收标准

### 功能验收

**R-001 优先级数据来源与默认值**

- [ ] **AC-001**（正例）Given CMDB 上某进程 `priority` 配置为 3，When 触发 CMDB 同步完成后查询该进程，Then bscp 侧该进程的优先级为 3，且任务详情中该进程实例的「进程优先级」列显示 `3`
- [ ] **AC-002**（反例）Given CMDB 上某进程 `priority` 为空或字段缺失，When 触发 CMDB 同步完成后对其执行 start，Then 该进程按优先级 0 参与编排，任务详情「进程优先级」列显示 `0`，且操作不报错
- [ ] **AC-003**（反例）Given bscp 侧无任何进程优先级编辑入口，When 用户在进程管理页查找修改优先级的操作，Then 页面不提供该入口；用户在 CMDB 修改后经同步生效

**R-002 排序方向**

- [ ] **AC-004**（正例）Given 同一业务下进程 A（priority=1）与进程 B（priority=2）各 1 个实例，When 执行 start，Then A 的实例任务先到达成功终态，B 的实例任务开始执行时间晚于 A 的结束时间
- [ ] **AC-005**（正例）Given 同上数据，When 执行 stop，Then B 的实例任务先到达成功终态，A 的实例任务开始执行时间晚于 B 的结束时间
- [ ] **AC-006**（正例）Given 同上数据，When 分别执行 reload 与 kill，Then 两者均按 A 先、B 后的顺序执行
- [ ] **AC-007**（正例）Given 同上数据，When 执行 restart，Then 按 B 先、A 后的顺序执行
- [ ] **AC-008**（反例/边界）Given 20 个进程实例的 `priority` 全部相同，When 执行 start，Then 批次数为 1，20 个实例任务并行下发，无跨批次串行等待，总耗时与改造前基线偏差 ≤ 5 秒

**R-003 托管类强制单批**

- [ ] **AC-009**（正例）Given 进程 A（priority=1）与进程 B（priority=2）各 1 个实例，When 执行 register，Then 两个实例任务在同一批并行下发，B 的开始执行时间不晚于 A 的结束时间
- [ ] **AC-010**（反例）Given 同上数据且进程 A 的 register 任务失败，When 任务批次结束，Then 进程 B 的 register 任务仍被执行（不因 A 失败而被优先级级联阻断），失败原因中不出现优先级阻断文案
- [ ] **AC-011**（正例）Given 同上数据，When 分别执行 unregister 与 update_register，Then 均为单批并行，行为同 AC-009

**R-004 分批串行**

- [ ] **AC-012**（正例）Given priority=1 的 5 个实例与 priority=2 的 5 个实例，When 执行 start，Then 先下发 5 个 priority=1 的任务，全部成功后再下发 5 个 priority=2 的任务；任务批次终态为 `succeed`，`total_count`=10、成功计数=10
- [ ] **AC-013**（反例/边界）Given priority=1 批次内某实例执行较慢（如耗时 60 秒），When 该批次执行中，Then 同批次其余 4 个实例不等待该慢实例，仍并行执行；仅 priority=2 批次等待整批结束

**R-005 失败门控与级联阻断**

- [ ] **AC-014**（正例）Given priority=1 的 2 个实例、priority=2 的 3 个实例、priority=3 的 4 个实例，且 priority=1 中有 1 个实例执行失败，When 批次执行结束，Then priority=2 与 priority=3 的全部 7 个实例任务状态为失败，失败原因为「优先级等于[1]的进程(...)操作已失败，优先级大于此的进程操作不会被继续执行」，且这 7 个任务计入批次失败计数
- [ ] **AC-015**（正例）Given 执行 stop 且 priority=3 批次中有 1 个实例失败，When 批次执行结束，Then priority=2 与 priority=1 的待执行任务状态为失败，失败原因为「优先级等于[3]的进程(...)操作已失败，优先级小于此的进程操作不会被继续执行」
- [ ] **AC-016**（反例）Given priority=1 批次内 2 个实例，其中实例 X 已失败、实例 Y 仍在执行中，When 触发级联阻断，Then 实例 Y 不被打断，继续执行至自身终态；若 Y 最终成功则保留成功状态
- [ ] **AC-017**（反例/边界）Given priority=1 批次 10 个实例中仅 1 个失败（失败率 10%），When 批次结束，Then 后续优先级批次**仍被阻断**（不因失败率低而放行）
- [ ] **AC-018**（正例）Given 全部批次全部实例成功，When 操作结束，Then 无任何任务带优先级阻断原因，批次终态为 `succeed`

**R-006 编排范围**

- [ ] **AC-019**（正例/边界）Given 一次操作范围表达式圈定 3 个集群、5 个模块、20 台主机上的实例，其中含 priority=1 与 priority=2，When 执行 start，Then 全部 priority=1 实例（跨集群/模块/主机）先执行完成，再执行 priority=2 实例，即共用一条串行链
- [ ] **AC-020**（正例）Given 分别通过进程 ID 列表、进程实例 ID 列表、操作范围表达式三种入口发起 start，When 各自执行，Then 三者的批次数与各批次内的实例集合完全相同
- [ ] **AC-021**（反例）Given 业务 A 与业务 B 各有 priority=1、priority=2 的实例，When 同时对两个业务分别发起 start，Then 两次操作各自独立编排（各产生 2 个批次），业务 B 的 priority=1 实例不等待业务 A 的任何批次完成
- [ ] **AC-022**（反例/边界）Given 一次操作仅命中单个集群单个模块内的 3 个实例且 priority 相同，When 执行 start，Then 批次数为 1，不因固定按业务的编排范围而产生额外批次或额外串行等待

**R-007 delete 拆解**

- [ ] **AC-023**（正例）Given 一次 delete 请求命中的实例中，含需 stop 的实例（priority=1 与 priority=2 各 1 个）与需 unregister 的实例（priority=1 与 priority=2 各 1 个），When 执行 delete，Then stop 分支按 priority=2 先、priority=1 后串行执行；unregister 分支两实例同批并行
- [ ] **AC-024**（反例）Given delete 请求命中的实例全部落入「直接删库」分支，When 执行 delete，Then 不创建优先级批次、不下发任务，实例被直接删除，行为与改造前一致

**R-008 重试语义**

- [ ] **AC-025**（正例）Given 某批次中 priority=1 有 1 个真实失败实例、priority=2 与 priority=3 各有 2 个被级联阻断的实例，When 用户对该批次执行失败重试，Then 重试集合包含全部 5 个任务，并按 priority=1 → 2 → 3 分批串行执行
- [ ] **AC-026**（反例）Given 重试过程中 priority=1 的任务再次失败，When 重试批次结束，Then priority=2 与 priority=3 的任务再次被级联阻断并给出优先级阻断原因

**R-009 超时处理**

- [ ] **AC-027**（正例）Given priority=1 批次中某实例所在主机 Agent 失联导致任务卡住，When 该任务达到现有步骤级超时（默认 3 分钟），Then 该任务状态为超时，后续优先级批次被级联阻断
- [ ] **AC-028**（反例）Given 系统未配置独立的批次级超时，When 批次内任务在步骤超时时间内正常结束，Then 不发生任何超时判定，批次正常推进到下一优先级

**F-008 UI 展示**

- [ ] **AC-029**（正例）Given 一个含多优先级实例的任务批次，When 用户打开任务详情页，Then 实例维度表格中存在「进程优先级」列并显示各实例优先级值；表格仍为扁平列表，不出现按优先级分组折叠或分阶段进度条
- [ ] **AC-030**（反例）Given 改造前产生的历史任务批次（无优先级信息），When 用户打开其任务详情，Then「进程优先级」列显示 `--`，页面其余内容正常渲染无报错

### 性能验收

- [ ] **AC-P01**：Given 单业务 2000 个进程实例、10 个不同 priority 取值，When 执行 start，Then 跨批次切换的额外等待（前批最大结束时间到后批最小开始时间）≤ 5 秒/批（通过 `task_records` 时间戳统计）
- [ ] **AC-P02**：Given 单批次 2000 个实例，When 该批次执行中，Then 同时处于 `running` 的实例任务数 ≤ 200，GSE 调用 QPS 不高于改造前基线（通过任务记录状态采样与 GSE 调用日志统计）
- [ ] **AC-P03**：Given 单次操作 5000 个实例、20 个不同 priority 取值，When 执行 start，Then 批次数为 20，全部批次按序执行完成，`task_batches.total_count` 等于 5000 且无任务丢失
- [ ] **AC-P04**：Given 未配置 priority（全部为 0）的业务 500 个实例，When 执行 start，Then 批次数为 1，总耗时相对改造前基线增幅 ≤ 5%（同环境连续 3 次取均值）

### 安全验收

- [ ] **AC-S01**：Given 无进程操作权限的用户，When 调用进程操作接口，Then 返回鉴权失败，错误码与改造前一致，且不因优先级改造放宽任何校验
- [ ] **AC-S02**：Given 用户仅有业务 A 的权限，When 对业务 A 发起按优先级的批量操作，Then 编排范围严格限定在业务 A 内，不涉及其他业务的进程实例

## 边界范围

### 本期包含

- CMDB `priority` 的同步与持久化（bscp 侧只读）
- start / reload / kill 升序，stop / restart 降序的分批编排
- 托管类操作（register / unregister / update_register）强制单批并行
- delete 拆解后各分支的优先级行为
- 批次串行门控（前批全部成功才发下批）
- 失败级联阻断及对齐 gsekit 的失败原因文案
- 失败重试按优先级重新编排
- 任务详情新增「进程优先级」列

### 本期不包含

- **聚合粒度配置能力**：不提供 gsekit `PROCESS_TASK_GRANULARITY` 那样的 BIZ / SET / MODULE / HOST 可配置粒度，固定按业务（等价于单次操作请求范围）
- **bscp 侧优先级编辑**：不提供优先级的新增/修改入口，不做与 CMDB 的双向同步或冲突合并
- **跨主机同名实例合并 GSE 请求**：不实现 gsekit 的 `local_inst_name` 跨主机合并 hosts 能力（该项只影响 GSE 调用次数与批量性，与启停顺序无关，属独立性能优化）
- **按优先级分组的 UI 展示**：不做分组折叠、分阶段进度条
- **用户可选的「是否按优先级串行」开关**：与 gsekit 一致，后端强制按优先级编排
- **独立的批次级超时机制**：复用现有任务步骤级超时
- **失败率阈值放行策略**：不提供「失败率低于阈值则继续」的配置
- **并发操作互斥**：不解决「同一业务同时发起两次操作（如 start 与 stop）导致两条串行链相互干扰」的问题，该问题为改造前既有行为，本期不扩大也不修复

## 约束条件

- **技术约束**：bscp 现有任务框架（基于 bcs-common task，Machinery + etcd + MySQL）中，任务批次仅做计数统计，**任务之间不具备依赖编排/串行等待能力**；实现批次串行门控需在该框架之上补齐编排语义，这是本需求的主要改造点与风险点
- **数据约束**：优先级生效依赖 CMDB 同步，现有定时同步默认 30 分钟一轮、每轮处理 10 个业务，且仅在 master 节点执行；CMDB 上的优先级变更不会即时生效
- **兼容约束**：`OperateProcess` 请求/响应结构不得新增字段，避免影响既有调用方
- **时间限制**：随迭代 1020451610002291414 交付
- **资源限制**：待迭代规划确认
