## 需求背景

### 业务背景

配置中心当前的项目（Project）与环境（Environment）主要以数值型 ID（ProjectID / EnvID）作为标识在系统内流转，Sidecar 与各个服务之间也以这两个 ID 关联。

实际业务场景中，项目在蓝鲸体系中通常以「项目标识（ProjectKey / project_id）」、环境以「环境名（EnvName）」作为业务侧稳定且可读的标识。当 Sidecar、前端或外部系统需要定位某个项目/环境时，若只能依赖内部数值 ID，则需要先做一次 ID 解析，增加了耦合与调用复杂度。

本需求的目标：提供按业务可读标识直接查询项目与环境的能力，并将 Sidecar 元数据中的标识改为 ProjectKey / EnvName，减少 ID 转换环节，使项目/环境定位更贴近业务语义。

### 用户故事

- 作为 **配置中心调用方（Sidecar / 前端 / 外部集成系统）**，我想要通过 ProjectKey 直接查询到对应项目、通过 EnvName（结合项目）直接查询到对应环境，以便于无需先持有内部数值 ID 即可定位资源。
- 作为 **Sidecar 上报链路**，我在元数据中使用 ProjectKey / EnvName 而非数值 ID，以便于与业务侧标识体系保持一致，降低标识转换成本。

### 详细功能描述

#### [F-001] 按 ProjectKey 查询项目

- **输入**：BizId（业务 ID）、ProjectKey（项目标识）
- **处理逻辑**：
  1. config-server 校验调用方对 BizId 的查询权限（FindBusinessResource）
  2. config-server 调用 data-service 的 `GetProjectByKey`
  3. data-service 通过 DAO 按 (BizID, Key) 查询项目记录，未命中返回 RecordNotFound
- **输出**：项目 Id、Spec、Attachment
- **边界条件**：
  - BizId / ProjectKey 不可为空
  - 同一 BizId 下 ProjectKey 唯一
- **异常处理**：
  - 项目不存在 → 返回「project does not exist」(RecordNotFound)
  - 数据库查询失败 → 返回 DBOpFailed

#### [F-002] 按 EnvName 查询环境

- **输入**：BizId、ProjectId、EnvName（环境名）
- **处理逻辑**：
  1. config-server 校验调用方对 BizId 的查询权限
  2. config-server 调用 data-service 的 `GetEnvironmentByName`
  3. data-service 通过 DAO 按 (BizID, ProjectID, EnvName) 查询环境记录，未命中返回 RecordNotFound
- **输出**：环境 Id、Spec、Attachment
- **边界条件**：
  - EnvName 在指定项目下唯一
- **异常处理**：
  - 环境不存在 → 返回 RecordNotFound

#### [F-003] Sidecar 元数据标识调整

- **输入**：Sidecar 上报时携带的元数据
- **处理逻辑**：
  1. `SidecarMetaHeader` 结构体字段由 `ProjectID uint32` / `EnvID uint32` 调整为 `ProjectKey string` / `EnvName string`
  2. 下游消费方（cache-service / feed-server 等）按新的字符串标识识别项目与环境
- **输出**：元数据以 ProjectKey / EnvName 透传
- **边界条件**：
  - 属于**不兼容变更**：旧版本 Sidecar 上报的 ProjectID/EnvID 字段不再适用，本次随代码落地采用新字段全量替换，旧版 Sidecar 需配套升级；过渡兼容方案可后续按需补充。
