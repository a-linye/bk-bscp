## 需求背景

### 业务背景

**本子需求解决的具体问题**：Wave 2 的编排引擎只覆盖了 start（升序）一种场景。而 gsekit 的实际行为中，不同操作类型的优先级方向并不相同——停止与重启是**降序**（先停高优先级，让上层依赖方先退出），重载与强制停止是**升序**；托管类操作则完全不参与优先级分批（gsekit 强制将其 priority 置 0）。此外 bscp 特有的 delete 操作会依据实例状态拆解为 stop / unregister / 直接删库三类分支，各分支的优先级语义不同。这些差异不补齐，父需求「严格对齐 gsekit」的目标就不成立。

**在整体需求中的定位**：本子需求在 Wave 2 引擎之上叠加操作类型维度的规则，把优先级编排从 start 一种场景扩展到全部 9 种操作类型。它不改动编排引擎的调度机制，只提供方向映射与分支归类，因此规模可控且可独立验证。

### 用户故事

作为 需要安全下线的业务运维人员
我想要 执行「停止」和「重启」时，优先级大的进程先被停止
以便于 上层依赖方先退出，避免被依赖进程先消失导致上层报错刷屏

作为 执行托管/取消托管的业务运维人员
我想要 托管类操作不因优先级被拆成多批串行
以便于 托管类操作不涉及启停依赖，不必为此付出串行等待的时间代价

## 功能需求

### 核心功能点

| 功能编号 | 功能描述 | 优先级 | 涉及角色 | 备注 |
|---------|---------|--------|---------|------|
| F-001 | 按操作类型确定优先级排序方向：stop/restart 降序，reload/kill 升序 | P0 | 业务运维 | 必须 |
| F-002 | 托管类操作（register / unregister / update_register）强制单波次并行 | P0 | 业务运维 | 必须 |
| F-003 | delete 语义拆解后各分支的优先级行为适配 | P1 | 业务运维 | 必须 |

### 详细功能描述

#### [F-001] 操作类型排序方向映射

- **输入**：一次进程操作请求的操作类型与待操作实例集合
- **处理逻辑**：
  1. 按操作类型查表确定优先级排序方向
  2. 将方向传入 Wave 2 编排引擎的排序分批环节，其余调度逻辑复用不变
- **方向映射表**（与 gsekit 严格一致）：

| 操作类型 | 排序方向 | 语义 |
|---------|---------|------|
| start（启动） | 升序（小 → 大） | 先启动低优先级（已由 Wave 2 实现） |
| reload（重载） | **升序** | 先重载低优先级 |
| kill（强制停止） | **升序** | 先强杀低优先级 |
| stop（停止） | **降序**（大 → 小） | 先停止高优先级 |
| restart（重启） | **降序** | 先重启高优先级 |
| register（托管） | 不分优先级 | 单波次并行，见 F-002 |
| unregister（取消托管） | 不分优先级 | 单波次并行，见 F-002 |
| update_register（更新托管配置） | 不分优先级 | 单波次并行，见 F-002 |
| delete（删除） | 依拆解分支而定 | 见 F-003 |

- **输出**：各操作类型按正确方向分波次串行执行
- **边界条件**：
  - 全部实例 priority 相同时，任何方向均退化为单波次并行
  - 方向仅影响波次间的执行顺序，不影响波次内的并行行为
- **异常处理**：
  - 出现映射表未覆盖的操作类型（如内部使用的 query_status）→ 不参与优先级编排，沿用改造前行为，并记录日志

#### [F-002] 托管类操作强制单波次

- **输入**：操作类型为 register、unregister、update_register 的请求
- **处理逻辑**：忽略实例间的实际 `priority` 差异，将全部实例归为同一波次并行执行
- **输出**：托管类操作无跨优先级串行等待，行为与改造前一致
- **边界条件**：
  - 即使实例间 `priority` 取值不同，也不拆分波次
  - `update_register` 为 bscp 特有操作（gsekit 无对应项），按父需求假设 A-2 归入托管类
- **异常处理**：
  - 托管类操作中某实例失败 → 沿用现有失败处理，不产生跨优先级级联阻断

#### [F-003] delete 拆解分支的优先级适配

- **输入**：操作类型为 delete 的请求
- **处理逻辑**：delete 依据实例状态与托管状态拆解为三类分支，各分支的优先级行为分别为：
  1. **stop 分支** → 按 `priority` **降序**分波次串行（与 stop 语义一致）
  2. **unregister 分支** → 同一波次并行，不分优先级（与托管类语义一致）
  3. **直接删库分支** → 不下发任务，不参与优先级编排
- **输出**：delete 的顺序行为与其拆解出的子操作语义保持一致
- **边界条件**：
  - 一次 delete 请求可能同时命中三类分支
  - 直接删库分支的实例不计入波次划分
- **异常处理**：
  - stop 分支失败时，级联规则由《批次失败级联阻断》承接，与 stop 操作一致

## 非功能需求

### 性能需求

- **方向映射开销**：方向判定为常量级查表，不引入额外的数据库查询或外部调用
  - 测量场景：单次操作 5000 个实例
  - 测量方式：对比同等规模 start 操作（Wave 2 基线）的波次划分耗时，偏差 ≤ 100 毫秒
- **托管类操作耗时**：托管类操作因强制单波次，总耗时相对改造前增幅 ≤ 5%
  - 测量场景：500 个实例、priority 取值各不相同、执行 register
  - 测量方式：同环境连续 3 次取均值

### 安全需求

- **权限控制**：沿用现有各操作类型的 IAM 鉴权，**不新增**权限点，不放宽任何现有校验
  - 测量方式：无对应操作权限的用户调用接口，返回鉴权失败，与改造前一致

## 验收标准

### 功能验收

**F-001 方向映射**

- [ ] **AC-001**（正例）Given 同一业务下进程 A（priority=1）与进程 B（priority=2）各 1 个实例，When 执行 stop，Then B 的实例任务先到达成功终态，A 的实例任务开始执行时间晚于 B 的结束时间
- [ ] **AC-002**（正例）Given 同上数据，When 执行 restart，Then 按 B 先、A 后的顺序执行
- [ ] **AC-003**（正例）Given 同上数据，When 分别执行 reload 与 kill，Then 两者均按 A 先、B 后的顺序执行
- [ ] **AC-004**（反例/边界）Given 20 个实例的 priority 全部相同，When 分别执行 stop 与 restart，Then 波次数均为 1，实例任务并行下发，无跨波次串行等待
- [ ] **AC-005**（反例）Given 服务端内部发起 query_status（映射表未覆盖的类型），When 执行，Then 不进行优先级分波次，沿用改造前行为并记录日志

**F-002 托管类单波次**

- [ ] **AC-006**（正例）Given 进程 A（priority=1）与进程 B（priority=2）各 1 个实例，When 执行 register，Then 两个实例任务在同一波次并行下发，B 的开始执行时间不晚于 A 的结束时间
- [ ] **AC-007**（反例）Given 同上数据且进程 A 的 register 任务失败，When 任务批次结束，Then 进程 B 的 register 任务仍被执行（不因 A 失败而被优先级级联阻断），失败原因中不出现优先级阻断文案
- [ ] **AC-008**（正例）Given 同上数据，When 分别执行 unregister 与 update_register，Then 均为单波次并行，行为同 AC-006

**F-003 delete 分支适配**

- [ ] **AC-009**（正例）Given 一次 delete 请求命中的实例中，含需 stop 的实例（priority=1 与 priority=2 各 1 个）与需 unregister 的实例（priority=1 与 priority=2 各 1 个），When 执行 delete，Then stop 分支按 priority=2 先、priority=1 后串行执行；unregister 分支两实例同波次并行
- [ ] **AC-010**（反例）Given delete 请求命中的实例全部落入「直接删库」分支，When 执行 delete，Then 不创建优先级波次、不下发任务，实例被直接删除，行为与改造前一致
- [ ] **AC-011**（反例/边界）Given delete 请求同时命中 stop、unregister、直接删库三类分支，When 执行 delete，Then 三类分支各按自身语义处理，直接删库的实例不计入波次划分，批次总数等于实际下发任务数

### 性能验收

- [ ] **AC-P01**：Given 单次操作 5000 个实例执行 stop，When 波次划分执行，Then 波次划分耗时相对同等规模 start 操作偏差 ≤ 100 毫秒
- [ ] **AC-P02**：Given 500 个实例、priority 取值各不相同，When 执行 register，Then 波次数为 1，总耗时相对改造前增幅 ≤ 5%（同环境连续 3 次取均值）

### 安全验收

- [ ] **AC-S01**：Given 无对应操作权限的用户，When 调用 stop / restart / register / delete 接口，Then 均返回鉴权失败，错误码与改造前一致

## 边界范围

### 本子需求包含

- stop / restart 降序，reload / kill 升序的方向映射
- 托管类操作（register / unregister / update_register）强制单波次并行
- delete 拆解后 stop 分支降序串行、unregister 分支单波次、直接删库不参与编排
- 映射表未覆盖操作类型的兜底行为

### 本子需求不包含

- **排序分批与波次串行门控的调度实现**：属《启动场景优先级分批串行编排》，本子需求仅提供方向参数与分支归类
- **start 升序**：已由《启动场景优先级分批串行编排》交付
- **失败级联阻断与阻断文案**：属《批次失败级联阻断》
- **失败重试的优先级重新编排**：属《失败重试按优先级重新编排》
- **priority 数据同步与任务详情展示**：属《优先级数据同步与详情展示》
- **delete 拆解规则本身的调整**：沿用改造前的拆解逻辑，本子需求只为已有分支补充优先级语义
