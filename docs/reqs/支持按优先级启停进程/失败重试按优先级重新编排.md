## 需求背景

### 业务背景

**本子需求解决的具体问题**：现有「失败重试」（RetryTasks）对批次内的失败任务并行重新下发，不做任何顺序编排。在引入优先级编排后，如果重试仍走并行路径，会出现一个自相矛盾的结果：首次执行严格保证了顺序，重试却退化为无序并发——用户处理完失败原因后重试，依赖顺序又一次得不到保证。

此外，Wave 3 的级联阻断会把后续优先级中未执行的任务置为失败。这些任务本身并没有真正执行过，重试时必须被包含进来，否则用户点了重试也只会重跑真实失败的那几个实例，被阻断的几百个实例仍然停在失败状态，需要用户重新发起一次完整操作。

**在整体需求中的定位**：本子需求是父需求的收口环节（Wave 4），保证「首次执行」与「重试执行」的顺序语义一致，使优先级编排能力在完整的操作闭环上成立。

### 用户故事

作为 处理完失败原因后重试的业务运维人员
我想要 重试同样按优先级分波次串行执行，且包含被前序失败连带阻断的任务
以便于 重试不会退化成无序并发，也不必为了覆盖被阻断的实例而重新发起一次完整操作

## 功能需求

### 核心功能点

| 功能编号 | 功能描述 | 优先级 | 涉及角色 | 备注 |
|---------|---------|--------|---------|------|
| F-001 | 重试集合收集：包含真实失败任务与被级联阻断的任务 | P0 | 业务运维 | 必须 |
| F-002 | 对重试集合按原操作类型的方向重新排序分波次并串行门控 | P0 | 业务运维 | 必须 |

### 详细功能描述

#### [F-001] 重试集合收集

- **输入**：用户对某个任务批次发起失败重试
- **处理逻辑**：
  1. 收集该批次中状态为失败的全部实例任务
  2. 集合必须**包含**被《批次失败级联阻断》置为失败的任务（即带优先级阻断文案、实际未执行过的任务）
  3. 已成功的任务不纳入重试集合
- **输出**：完整的重试任务集合
- **边界条件**：
  - 重试集合中若只剩单一优先级 → 单波次并行
  - 重试集合为空（批次全部成功）→ 沿用现有校验，不创建重试批次
- **异常处理**：
  - 重试集合中的进程实例在原批次执行后已从 CMDB 同步中删除 → 沿用现有实例有效性校验，跳过该实例并在结果中标注

#### [F-002] 重试的优先级重新编排

- **输入**：F-001 产出的重试集合、原批次的操作类型
- **处理逻辑**：
  1. 取重试集合中各实例所属进程的当前 `priority`（以重试时刻的最新同步值为准）
  2. 按原批次的操作类型确定排序方向（复用《停止重启等操作方向适配》的方向映射）
  3. 复用 Wave 2 编排引擎完成排序分波次与波次串行门控
  4. 重试过程中若某波次非全部成功 → 复用 Wave 3 的级联阻断，后续波次任务同样被阻断并写入阻断文案
- **输出**：重试执行具备与首次执行完全相同的顺序保证与阻断语义
- **边界条件**：
  - 重试使用重试时刻的最新 priority，而非原批次执行时的快照值（因优先级唯一数据源为 CMDB，可能已变更）
  - 托管类操作的重试仍为单波次并行，不因重试而引入串行
- **异常处理**：
  - 重试过程中再次出现波次失败 → 同样触发级联阻断，行为与首次执行一致

## 接口契约定义

## 非功能需求

### 性能需求

- **重试编排开销**：重试的波次划分与门控行为与首次执行一致，跨波次切换额外等待 ≤ 5 秒/波次
  - 测量场景：重试集合 2000 个实例、10 个不同 priority 取值
  - 测量方式：对比实例任务记录中相邻波次的时间戳
- **重试集合收集耗时**：从发起重试到重试批次创建完成 ≤ 3 秒
  - 测量场景：原批次 5000 个实例中 4750 个为被阻断任务
  - 测量方式：对比重试请求响应时间

### 安全需求

- **权限控制**：沿用现有重试接口的 IAM 鉴权，**不新增**权限点，不放宽任何现有校验
  - 测量方式：无进程操作权限的用户调用重试接口，返回鉴权失败，与改造前一致

## 验收标准

### 功能验收

**F-001 重试集合收集**

- [ ] **AC-001**（正例）Given 某批次中 priority=1 有 1 个真实失败实例、priority=2 与 priority=3 各有 2 个被级联阻断的实例，When 用户对该批次执行失败重试，Then 重试集合包含全部 5 个任务
- [ ] **AC-002**（反例）Given 某批次中有 3 个已成功实例与 2 个失败实例，When 执行重试，Then 重试集合仅含 2 个失败实例，3 个已成功实例不被重复执行
- [ ] **AC-003**（反例/边界）Given 某批次全部实例成功，When 用户尝试发起重试，Then 沿用现有校验返回提示，不创建重试批次
- [ ] **AC-004**（反例）Given 重试集合中某进程实例在原批次执行后已从 CMDB 同步中删除，When 执行重试，Then 沿用现有实例有效性校验跳过该实例，并在重试结果中标注，其余实例正常重试

**F-002 重试的优先级重新编排**

- [ ] **AC-005**（正例）Given 重试集合含 priority=1、2、3 各若干实例且原操作为 start，When 执行重试，Then 按 priority=1 → 2 → 3 分波次串行执行，每个波次全部成功后才下发下一波次
- [ ] **AC-006**（正例）Given 原批次操作类型为 stop，When 执行重试，Then 重试按 priority 降序分波次串行，方向与原操作一致
- [ ] **AC-007**（反例）Given 重试过程中 priority=1 的任务再次失败，When 重试批次结束，Then priority=2 与 priority=3 的任务再次被级联阻断并给出优先级阻断原因
- [ ] **AC-008**（正例/边界）Given 重试集合中全部实例的 priority 相同，When 执行重试，Then 波次数为 1，实例并行重试，无跨波次串行等待
- [ ] **AC-009**（正例）Given 某实例的 priority 在原批次执行后已在 CMDB 上被修改并完成同步，When 执行重试，Then 该实例按重试时刻的最新 priority 参与波次划分
- [ ] **AC-010**（反例）Given 原批次操作类型为 register（托管类），When 执行重试，Then 重试为单波次并行，不因重试引入跨优先级串行

### 性能验收

- [ ] **AC-P01**：Given 重试集合 2000 个实例、10 个不同 priority 取值，When 执行重试，Then 跨波次切换的额外等待 ≤ 5 秒/波次（通过实例任务记录时间戳统计）
- [ ] **AC-P02**：Given 原批次 5000 个实例中 4750 个为被阻断任务，When 发起重试，Then 从请求发起到重试批次创建完成 ≤ 3 秒

## 边界范围

### 本子需求包含

- 重试集合收集，含被级联阻断的任务
- 重试按原操作类型方向重新排序分波次
- 重试复用波次串行门控与级联阻断语义
- 重试使用重试时刻的最新 priority
- 托管类操作重试保持单波次并行

### 本子需求不包含

- **排序分批与波次串行门控的调度实现**：属《启动场景优先级分批串行编排》
- **方向映射表**：属《停止重启等操作方向适配》
- **级联阻断判定与文案**：属《批次失败级联阻断》
- **重试接口本身的改造**：接口结构保持现状，仅内部编排行为变化
- **单任务级别的重试入口**：沿用现有批次级重试语义，不新增单实例重试能力
- **自动重试**：不引入失败后自动重试机制，重试仍由用户显式发起

## 工时估算

- 估时依据：命中「单模块逻辑」基线（4–12h，中值 8h）。编排引擎、方向映射、级联阻断均已由前序波次就绪，本子需求在重试入口单一模块内完成集合收集与引擎复用。影响 M 的维度为依赖（需同时对接 Wave 2 引擎与 Wave 3 阻断产物）。M 明细：重试集合收集（含被阻断任务）3h + 复用编排引擎重新分波次 3h + 测试 2h = 8h
- 调整因子：可复用基础设施/框架（-20%，排序分批、方向映射、波次门控与级联阻断全部可直接复用，本子需求无新增机制）→ M = 8 × 0.8 = 6.4 ≈ 6.5h
- PERT：O=4h，M=6.5h，P=16h，E=(4 + 4×6.5 + 16)/6 = 46/6 = 7.67 ≈ 7.5h
- 预估工时：7.5h

> ℹ️ E=7.5h 略低于拆分指南建议的 8 人时下限。经评估**不与《批次失败级联阻断》合并**，理由：一是重试为独立的用户入口（RetryTasks）与独立可演示场景，合并会削弱可独立验证性；二是合并后工时达 24 人时，正好贴死强约束上限而无任何缓冲。
