## 需求背景

### 业务背景

**本子需求解决的具体问题**：bscp 现有 `OperateProcess` 把每个进程实例单独构建为一个任务并立即 `Dispatch` 到 200 worker 的全局并发池，任务之间没有任何依赖编排能力——任务批次仅做计数统计，不具备「等上一批完成再发下一批」的语义。因此即使拿到了 CMDB 的优先级数据，也无法保证执行顺序。这是父需求的主要改造点与技术风险点。

**在整体需求中的定位**：本子需求是父需求的核心 MVP（Wave 2）。它把范围收窄到**启动（start）场景**，端到端建立完整的优先级编排能力：按优先级升序分批、同优先级批内并行、跨优先级串行门控、编排状态持久化。范围收窄的目的是让核心编排引擎在一个可独立演示、可独立验证的最小场景中先跑通并暴露技术风险；其余操作类型的方向适配（stop/restart 降序等）由 Wave 3 的《停止重启等操作方向适配》在本引擎之上叠加，失败级联由 Wave 3 的《批次失败级联阻断》挂载到本子需求定义的波次终态回调上。

选择「按操作类型范围递进」而非「按技术层次」拆分本引擎，原因是技术层次拆分（如「排序分批」与「批次门控」各成一卡）会导致两卡均不可独立演示，落入反模式；而按 start 场景收窄可保证第一刀就是能端到端跑通的骨架。

### 用户故事

作为 存在启动依赖关系的业务运维人员
我想要 执行「启动」时，优先级小的进程先启动完成，再启动优先级大的进程
以便于 被依赖的进程先就绪，依赖方不再因为对端未启动而失败

## 功能需求

### 核心功能点

| 功能编号 | 功能描述 | 优先级 | 涉及角色 | 备注 |
|---------|---------|--------|---------|------|
| F-001 | 按 priority 升序对 start 操作的待操作实例排序并划分波次 | P0 | 业务运维 | 必须 |
| F-002 | 波次串行门控：本波次全部实例任务成功后才下发下一波次 | P0 | 业务运维 | 必须 |
| F-003 | 编排状态持久化与服务重启恢复 | P0 | 研发 | 必须 |

### 详细功能描述

#### [F-001] 按优先级升序排序与波次划分

- **输入**：一次 start 操作请求，待操作的进程实例集合（可来自进程 ID 列表、进程实例 ID 列表、操作范围表达式三种入口）
- **处理逻辑**：
  1. 解析出本次待操作的全部进程实例
  2. 取每个实例所属进程的 `priority`（引用 Wave 1 契约，缺省 0）
  3. 按 `priority` **升序**排序
  4. 按 `priority` 分组：同一 `priority` 的所有实例归为一个波次
  5. 生成有序波次序列，波次序号自 1 递增，与执行顺序一致
- **输出**：按优先级升序有序的波次序列，全部实例任务按 Wave 1 契约落库并标注波次归属
- **边界条件**：
  - 全部实例 `priority` 相同 → 只有一个波次，等价于改造前的并行行为，不引入串行等待
  - 单个实例 → 一个波次
  - priority 为负数时排在 0 之前
  - 三种操作入口适用同一编排规则，波次划分结果一致
- **异常处理**：
  - 待操作实例集合为空 → 沿用现有校验，不创建批次

#### [F-002] 波次串行门控

- **输入**：F-001 产出的有序波次序列
- **处理逻辑**：
  1. 下发当前波次内全部实例任务，波次内并行执行
  2. 等待本波次全部实例任务到达终态（通过 Wave 1 契约定义的波次终态回调感知）
  3. 本波次全部实例任务终态为成功 → 下发下一波次
  4. 本波次存在非成功终态 → 停止下发后续波次，触发波次终态回调（由《批次失败级联阻断》挂载处理）
  5. 重复至波次序列耗尽
- **输出**：波次按序执行；批次统计与终态沿用现有任务批次机制（`running` → `succeed` / `failed` / `partly_failed`）
- **边界条件**：
  - 单个实例任务的成功判定沿用现有实例任务内部步骤（其中已含 GSE 进程状态校验与收尾），**不新增独立的波次级 GSE 状态复查环节**
  - 波次内不额外限制并发规模，沉降到现有 200 worker 全局并发池自然限流
  - 波次内的慢实例不阻塞同波次其他实例，仅阻塞下一波次的下发
- **异常处理**：
  - 实例任务长时间不结束（如 Agent 失联）→ 沿用现有任务步骤级超时（默认 3 分钟）判定为超时，超时视为非成功终态，停止下发后续波次；**不引入独立的波次级超时**

#### [F-003] 编排状态持久化与重启恢复

- **输入**：波次序列与当前执行进度
- **处理逻辑**：
  1. 波次划分结果与当前执行到第几个波次的进度按 Wave 1 契约持久化
  2. 服务重启后，能根据持久化状态识别未完成的批次及其当前波次
  3. 对未完成批次继续按门控规则推进后续波次
- **输出**：编排进度不因服务重启丢失
- **边界条件**：
  - 重启瞬间处于执行中的实例任务由现有任务框架机制处理，本子需求不改变其行为
  - 仅 master 节点推进编排，避免多节点重复下发
- **异常处理**：
  - 持久化状态与实际任务记录不一致 → 以实例任务记录的实际终态为准重新判定波次是否可推进，并记录告警日志

#### [F-004] 编排范围与入口一致性

- **输入**：三种操作入口发起的 start 请求
- **处理逻辑**：
  1. 优先级串行链的生效范围为一次操作请求内。由于一次 `OperateProcess` 请求本身限定单个业务，等价于 gsekit 默认的业务（BIZ）聚合粒度
  2. 同一次操作内跨集群、跨模块、跨主机的实例共用一条串行链
  3. 不同操作请求之间相互独立编排，互不等待
- **输出**：编排范围明确且三种入口一致
- **边界条件**：
  - 本期不提供 BIZ/SET/MODULE/HOST 聚合粒度配置能力
  - 编排范围严格限定在请求所属业务内，不跨业务
- **异常处理**：
  - 同一业务并发发起多次操作 → 各请求独立编排（该场景的串行链相互干扰问题为改造前既有行为，本期不扩大也不修复）

## 接口契约定义

引用《优先级数据同步与详情展示》定义的批次编排数据契约，本子需求不重复定义。

## 非功能需求

### 性能需求

- **波次切换开销**：跨优先级波次切换引入的额外等待（从本波次最后一个任务到达终态，到下一波次首个任务开始执行）**≤ 5 秒**
  - 测量场景：单业务 2000 个进程实例、10 个不同 `priority` 取值、执行 start
  - 测量方式：对比实例任务记录中相邻波次的时间戳（前波次最大结束时间 vs 后波次最小开始时间）
- **波次内并发**：波次内不额外限制并发，沉降到现有 200 worker 全局并发池
  - 测量场景：单波次 2000 个实例
  - 测量方式：观测同时处于 `running` 的实例任务数 ≤ 200，且 GSE 调用 QPS 不高于改造前基线
- **规模能力**：单次操作 ≤ 5000 个进程实例、≤ 20 个不同 `priority` 取值时功能正常
  - 测量场景：构造 5000 实例 / 20 个优先级取值的 start 操作
  - 测量方式：波次数等于优先级取值数，全部波次按序执行完成，批次总数与实际实例数一致且无任务丢失
- **向后兼容开销**：未配置 priority（全部为 0）的业务执行 start 时，总耗时相对改造前增幅 ≤ 5%
  - 测量场景：500 个实例、priority 全为 0
  - 测量方式：同环境连续 3 次取均值

### 安全需求

- **权限控制**：沿用现有 `OperateProcess` 的 IAM 鉴权，**不新增**权限点，不放宽任何现有校验
  - 测量方式：无进程操作权限的用户调用接口，返回鉴权失败，与改造前一致
- **数据隔离**：编排范围严格限定在请求所属业务内
  - 测量方式：仅有业务 A 权限的用户发起操作，编排涉及的实例全部属于业务 A

## 验收标准

### 功能验收

**F-001 排序与波次划分**

- [ ] **AC-001**（正例）Given 同一业务下进程 A（priority=1）与进程 B（priority=2）各 1 个实例，When 执行 start，Then A 的实例任务先到达成功终态，B 的实例任务开始执行时间晚于 A 的结束时间
- [ ] **AC-002**（反例/边界）Given 20 个进程实例的 `priority` 全部相同，When 执行 start，Then 波次数为 1，20 个实例任务并行下发，无跨波次串行等待，总耗时与改造前基线偏差 ≤ 5 秒
- [ ] **AC-003**（正例）Given 分别通过进程 ID 列表、进程实例 ID 列表、操作范围表达式三种入口发起 start，When 各自执行，Then 三者的波次数与各波次内的实例集合完全相同
- [ ] **AC-004**（反例/边界）Given 待操作实例集合为空，When 发起 start，Then 沿用现有校验返回错误，不创建任务批次

**F-002 波次串行门控**

- [ ] **AC-005**（正例）Given priority=1 的 5 个实例与 priority=2 的 5 个实例，When 执行 start，Then 先下发 5 个 priority=1 的任务，全部成功后再下发 5 个 priority=2 的任务；任务批次终态为 `succeed`，批次总数为 10、成功计数为 10
- [ ] **AC-006**（反例/边界）Given priority=1 波次内某实例执行较慢（如耗时 60 秒），When 该波次执行中，Then 同波次其余 4 个实例不等待该慢实例，仍并行执行；仅 priority=2 波次等待整个波次结束
- [ ] **AC-007**（反例）Given priority=1 波次中有 1 个实例失败，When 该波次全部任务到达终态，Then 不再下发 priority=2 波次的任务，并触发波次终态回调（阻断处理由《批次失败级联阻断》承接）
- [ ] **AC-008**（正例）Given 全部波次全部实例成功，When 操作结束，Then 无任何任务带优先级阻断原因，批次终态为 `succeed`
- [ ] **AC-009**（反例）Given priority=1 波次中某实例所在主机 Agent 失联，When 该任务达到现有步骤级超时（默认 3 分钟）判定为超时，Then 不再下发后续波次；系统未配置独立的波次级超时

**F-003 编排状态持久化与重启恢复**

- [ ] **AC-010**（正例）Given 一个含 3 个波次的 start 批次执行到第 2 个波次，When data-service 重启后恢复，Then 该批次的波次划分与执行进度完整保留，第 3 个波次在第 2 个波次满足门控条件后被正常下发
- [ ] **AC-011**（反例）Given 持久化的波次进度与实例任务实际终态不一致，When 编排推进判定执行，Then 以实例任务记录的实际终态为准判定，并输出告警日志，不出现重复下发同一波次

**F-004 编排范围**

- [ ] **AC-012**（正例/边界）Given 一次操作范围表达式圈定 3 个集群、5 个模块、20 台主机上的实例，其中含 priority=1 与 priority=2，When 执行 start，Then 全部 priority=1 实例（跨集群/模块/主机）先执行完成，再执行 priority=2 实例，即共用一条串行链
- [ ] **AC-013**（反例）Given 业务 A 与业务 B 各有 priority=1、priority=2 的实例，When 同时对两个业务分别发起 start，Then 两次操作各自独立编排（各产生 2 个波次），业务 B 的 priority=1 实例不等待业务 A 的任何波次完成
- [ ] **AC-014**（反例/边界）Given 一次操作仅命中单个集群单个模块内的 3 个实例且 priority 相同，When 执行 start，Then 波次数为 1，不因固定按业务的编排范围而产生额外波次或额外串行等待

## 边界范围

### 本子需求包含

- start 操作按 priority 升序排序与波次划分
- 波次串行门控：本波次全部成功才下发下一波次
- 波次终态回调的触发（供失败级联挂载）
- 编排状态持久化与服务重启恢复
- 编排范围限定单次操作请求内（单业务），三种操作入口行为一致
- 未配置优先级业务的向后兼容（退化为单波次并行）

### 本子需求不包含

- **stop/restart 降序与 reload/kill 升序的方向映射**：属《停止重启等操作方向适配》
- **托管类操作单批与 delete 三分支适配**：属《停止重启等操作方向适配》
- **失败级联阻断、待执行任务置失败与阻断文案**：属《批次失败级联阻断》，本子需求仅提供回调触发点
- **失败重试的优先级重新编排**：属《失败重试按优先级重新编排》
- **priority 数据同步与任务详情展示**：属《优先级数据同步与详情展示》
- **聚合粒度配置能力**（BIZ/SET/MODULE/HOST）：父需求已明确排除
- **同一业务并发操作的互斥**：父需求已明确排除，为改造前既有行为
- **波次级独立超时机制**：父需求已明确排除，复用任务步骤级超时
- **失败率阈值放行策略**：父需求已明确排除

## 工时估算

- 估时依据：命中「架构变更」基线下界（24–80h）。核心是在现有任务框架（bcs-common task，Machinery + etcd + MySQL）之上补齐任务间依赖编排语义——现有批次仅做计数统计，无串行等待能力。影响 M 的维度为技术复杂度（波次状态机、并发时序、重启恢复）与风险（改动核心任务下发链路）。M 明细：排序与波次划分 2h + 编排状态持久化 5h + 波次完成检测与下一波次下发 7h + 单测与集成验证 4h = 18h
- 调整因子：技术难度高（+40%，波次状态机涉及并发时序与服务重启恢复，团队无现成编排能力）、可复用基础设施/框架（-20%，现有任务批次机制与回调可复用）→ 净 +20%，M = 18 × 1.2 = 21.6 ≈ 21.5h
- PERT：O=12h，M=21.5h，P=40h，E=(12 + 4×21.5 + 40)/6 = 138/6 = 23h
- 预估工时：23h

> ⚠️ 本子需求 E=23h，接近 24 人时强约束上限，缓冲仅 1 人时。开发过程中若波次状态机或重启恢复出现返工，应及早触发二次拆分（可按「排序分批 + 门控」与「持久化 + 重启恢复」切分）。
