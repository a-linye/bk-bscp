## 需求背景

### 业务背景

**本子需求解决的具体问题**：Wave 2 的编排引擎在某个波次未全部成功时会停止下发后续波次，但仅仅「不下发」是不够的——用户在任务详情里看到的会是一批状态不明的任务，无法分清「进程本身操作失败」和「因前序优先级失败而根本没执行」。gsekit 的做法是把后续优先级中仍待执行的任务直接置为失败，并写入明确的原因文案（区分升序/降序两种表述），使失败面一目了然。父需求已确认严格对齐这一行为。

同时，本子需求还要处理一个容易被忽略的边界：波次内已在执行中的任务**不能**被打断，已成功的任务必须保留成功状态——阻断只作用于「尚未执行」的任务。

**在整体需求中的定位**：本子需求把 Wave 2 的「停止下发」升级为完整的「失败即止 + 失败可定位」，是父需求 US-4 与 US-5 的落地。它挂载在 Wave 2 定义的波次终态回调上，不改动调度机制本身。

### 用户故事

作为 批量操作的业务运维人员
我想要 某个优先级波次没有全部成功时，后续优先级的进程不再被执行
以便于 依赖链断裂时立即止损，而不是在错误的前提下继续操作后面几百个实例

作为 排查操作失败的业务运维人员
我想要 被前序优先级失败连带阻断的任务有明确的失败原因
以便于 一眼分清「进程本身操作失败」和「被前序失败连带阻断」，只重点排查真正的失败源

## 功能需求

### 核心功能点

| 功能编号 | 功能描述 | 优先级 | 涉及角色 | 备注 |
|---------|---------|--------|---------|------|
| F-001 | 波次门控判定：非全部成功即阻断后续全部优先级 | P0 | 业务运维 | 必须 |
| F-002 | 将后续优先级中尚未执行的任务置为失败并写入对齐 gsekit 的原因文案 | P0 | 业务运维 | 必须 |
| F-003 | 执行中任务不打断、已成功任务保留成功 | P0 | 业务运维 | 必须 |
| F-004 | 超时终态纳入非成功判定并触发级联 | P0 | 业务运维 | 必须 |

### 详细功能描述

#### [F-001] 波次门控判定

- **输入**：某个优先级波次的全部实例任务终态（通过 Wave 2 的波次终态回调获得）
- **处理逻辑**：
  1. 判定该波次是否全部实例任务均为成功终态
  2. 存在任一非成功终态（失败或超时）→ 触发级联阻断（转 F-002）
  3. 全部成功 → 不触发阻断，由 Wave 2 引擎继续下发下一波次
- **输出**：阻断决策
- **边界条件**：
  - 判定标准为「非全部成功即阻断」，**不设失败率阈值**——波次内 10 个实例仅 1 个失败也会阻断
  - 阻断范围为本次操作请求内（单业务）的后续全部优先级
- **异常处理**：
  - 波次内既有成功又有失败 → 后续波次仍被阻断

#### [F-002] 级联置失败与原因文案

- **输入**：触发阻断的波次优先级值、操作类型的排序方向、后续优先级中尚未执行的任务集合
- **处理逻辑**：
  1. 从 Wave 1 契约定义的「待执行」任务中，筛选出后续全部优先级的任务
  2. 将这些任务状态置为失败
  3. 为每个任务写入明确的失败原因文案，按排序方向区分表述：
     - **升序操作**（start / reload / kill）：`优先级等于[X]的进程(...)操作已失败，优先级大于此的进程操作不会被继续执行`
     - **降序操作**（stop / restart）：`优先级等于[X]的进程(...)操作已失败，优先级小于此的进程操作不会被继续执行`
  4. 这些任务计入批次的失败计数，批次终态按现有机制判定
- **输出**：任务详情中被阻断的任务显示为失败，失败原因指明前序优先级失败
- **边界条件**：
  - 文案中的优先级值 X 为触发阻断的波次优先级值
  - 被级联阻断的任务与真实失败任务在批次统计中合并计入「失败」（对齐 gsekit，见父需求未决问题 Q-004）
  - 托管类操作不产生跨优先级级联（由《停止重启等操作方向适配》保证其为单波次）
- **异常处理**：
  - 待执行任务集合为空（阻断发生在最后一个波次）→ 不做任何状态更新，批次正常收敛为终态

#### [F-003] 执行中与已成功任务的保护

- **输入**：触发阻断时本波次内各实例任务的实时状态
- **处理逻辑**：
  1. 本波次内已在执行中的任务**不打断**，让其自然执行至自身终态
  2. 已成功的任务保留成功状态，不因同波次其他实例失败而被改写
  3. 阻断只作用于「尚未执行」语义的任务
- **输出**：阻断行为不影响已启动的执行流
- **边界条件**：
  - 执行中任务最终成功则保留成功；最终失败则按自身失败原因记录，不覆盖为优先级阻断文案
- **异常处理**：
  - 执行中任务在阻断后才达到超时 → 按超时记录自身终态，不改写为阻断文案

#### [F-004] 超时纳入非成功判定

- **输入**：实例任务因 Agent 失联等原因长时间不结束
- **处理逻辑**：
  1. 沿用现有任务步骤级超时（默认 3 分钟）判定该实例任务为超时
  2. 超时视为非成功终态，参与 F-001 的波次门控判定并触发级联阻断
- **输出**：卡住的任务不会无限期阻塞批次，且会正确触发级联
- **边界条件**：
  - **不引入独立的波次级超时机制**，完全依赖现有步骤级超时兜底
- **异常处理**：
  - 波次内任务在步骤超时时间内正常结束 → 不发生任何超时判定，批次正常推进

## 非功能需求

### 性能需求

- **级联阻断耗时**：从波次终态回调触发到后续全部待执行任务状态更新完成 ≤ 3 秒
  - 测量场景：单次操作 5000 个实例、20 个优先级取值，在第 1 个波次触发阻断（需批量更新约 4750 个任务）
  - 测量方式：对比回调触发时间戳与最后一条任务状态更新时间戳
- **批量更新开销**：级联置失败采用批量更新，不产生逐条更新的数据库压力
  - 测量场景：同上
  - 测量方式：统计状态更新产生的数据库写请求数，应为常量级批次数而非实例数量级

### 安全需求

- **权限控制**：级联阻断为服务端内部行为，不新增对外接口与权限点
  - 测量方式：确认无新增 API 与权限点
- **数据隔离**：阻断范围严格限定在触发阻断的批次内，不影响其他批次或其他业务
  - 测量方式：业务 A 的批次触发阻断时，业务 B 的并发批次任务状态不受影响

## 验收标准

### 功能验收

**F-001 波次门控判定**

- [ ] **AC-001**（正例）Given priority=1 的 2 个实例、priority=2 的 3 个实例、priority=3 的 4 个实例，且 priority=1 中有 1 个实例执行失败，When 波次执行结束，Then priority=2 与 priority=3 的全部 7 个实例任务状态为失败，且这 7 个任务计入批次失败计数
- [ ] **AC-002**（反例/边界）Given priority=1 波次 10 个实例中仅 1 个失败（失败率 10%），When 波次结束，Then 后续优先级波次仍被阻断，不因失败率低而放行
- [ ] **AC-003**（正例）Given 全部波次全部实例成功，When 操作结束，Then 无任何任务带优先级阻断原因，批次终态为 `succeed`

**F-002 级联置失败与文案**

- [ ] **AC-004**（正例）Given 执行 start 且 priority=1 波次中有 1 个实例失败，When 波次执行结束，Then 后续波次任务的失败原因为「优先级等于[1]的进程(...)操作已失败，优先级大于此的进程操作不会被继续执行」
- [ ] **AC-005**（正例）Given 执行 stop 且 priority=3 波次中有 1 个实例失败，When 波次执行结束，Then priority=2 与 priority=1 的待执行任务状态为失败，失败原因为「优先级等于[3]的进程(...)操作已失败，优先级小于此的进程操作不会被继续执行」
- [ ] **AC-006**（反例/边界）Given 阻断发生在最后一个波次（无后续待执行任务），When 该波次结束，Then 不做任何额外状态更新，批次正常收敛为终态且不出现异常日志
- [ ] **AC-007**（正例）Given 被级联阻断的任务与真实失败任务同时存在，When 用户查看任务详情，Then 两类任务均计入失败计数，且可通过失败原因文案区分二者

**F-003 执行中与已成功任务保护**

- [ ] **AC-008**（反例）Given priority=1 波次内 2 个实例，其中实例 X 已失败、实例 Y 仍在执行中，When 触发级联阻断，Then 实例 Y 不被打断，继续执行至自身终态；若 Y 最终成功则保留成功状态
- [ ] **AC-009**（反例）Given priority=1 波次内实例 Y 在阻断触发后才达到超时，When Y 到达终态，Then Y 记录为超时并保留自身失败原因，不被改写为优先级阻断文案
- [ ] **AC-010**（正例）Given priority=1 波次内 5 个实例中 3 个已成功、1 个失败、1 个执行中，When 触发级联阻断，Then 3 个已成功的任务保留成功状态不被改写

**F-004 超时纳入判定**

- [ ] **AC-011**（正例）Given priority=1 波次中某实例所在主机 Agent 失联导致任务卡住，When 该任务达到现有步骤级超时（默认 3 分钟），Then 该任务状态为超时，后续优先级波次被级联阻断
- [ ] **AC-012**（反例）Given 系统未配置独立的波次级超时，When 波次内任务在步骤超时时间内正常结束，Then 不发生任何超时判定，批次正常推进到下一优先级

### 性能验收

- [ ] **AC-P01**：Given 单次操作 5000 个实例、20 个优先级取值，在第 1 个波次触发阻断，When 级联阻断执行，Then 从回调触发到最后一条任务状态更新完成 ≤ 3 秒
- [ ] **AC-P02**：Given 同上场景，When 级联置失败执行，Then 状态更新产生的数据库写请求数为常量级批次数（不随实例数量线性增长）

### 安全验收

- [ ] **AC-S01**：Given 业务 A 的批次触发级联阻断，When 业务 B 存在并发执行的批次，Then 业务 B 的任务状态完全不受影响

## 边界范围

### 本子需求包含

- 波次门控判定：非全部成功即阻断（无失败率阈值）
- 后续全部优先级中尚未执行任务的级联置失败
- 对齐 gsekit 的失败原因文案（升序/降序两种表述）
- 被阻断任务计入批次失败计数
- 执行中任务不打断、已成功任务保留成功
- 超时终态纳入非成功判定并触发级联

### 本子需求不包含

- **排序分批与波次串行门控的调度实现**：属《启动场景优先级分批串行编排》，本子需求挂载在其波次终态回调上
- **各操作类型的排序方向映射**：属《停止重启等操作方向适配》，本子需求仅按方向选择文案表述
- **失败重试的优先级重新编排**：属《失败重试按优先级重新编排》
- **待执行任务的落库机制**：属《优先级数据同步与详情展示》的契约与实现
- **区分「真失败」与「被连带阻断」的独立统计口径**：父需求已确认合并计入失败（对齐 gsekit），相关讨论保留为未决问题 Q-004
- **失败率阈值放行策略**：父需求已明确排除
- **独立的波次级超时机制**：父需求已明确排除
