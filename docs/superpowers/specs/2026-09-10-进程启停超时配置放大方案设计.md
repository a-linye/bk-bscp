# 进程启停超时配置放大方案设计

- 日期：2026-09-10
- 范围：普通进程启停任务（`process_operate`）
- 交付形式：**仅调整 `bk-bscp.yaml` 配置项，不改代码**

## 1. 背景与问题

gsekit 侧反馈，部分用户在 CMDB 进程属性里把「操作超时时长」（`op_timeout`）配到了 10 分钟量级。Windows 主机上的进程启停确实可能耗时这么久。

BSCP 当前的表现是：进程实际已经停成功，但任务被判失败。典型报错链是两段的，容易误判：

```
# 第一段（真正的问题）：等不到 GSE 结果，任务判失败
[Operate STEP]: process operate failed, errorCode=115

# 第二段（用户实际看到的）：重试时被前置校验挡住
step ValidateOperateProcess running failed, err=process cannot operate,
reason: process is already stopped, no need to stop or kill
```

第二段其实是**第一段的后果，不是独立故障**。第一次任务超时判失败后，`Callback` 会重新查 GSE 真实状态并回写数据库（此时进程已停），实例状态变成 `stopped`；用户再点一次停止，`CanProcessOperate` 就以"已停止无需停止"拒绝。也就是说这条报错反而证明上一次操作是生效的。

### 根因

GSE 侧的操作超时是**每个进程独立配置**的，BSCP 会原样透传：

```go
// internal/processor/gse/gse.go:98-101
opTimeout := params.ProcessInfo.Timeout   // 来自 CMDB 进程属性
if opTimeout == 0 {
    opTimeout = DefaultOpTimeout          // 兜底 60s
}
```

而 BSCP 自己的等待时长是**全局固定**的，且两个关键数字恰好都是 180 秒，互相顶死：

| 层 | 位置 | 当前值 |
|---|---|---|
| GSE 结果轮询上限 | `ProcessPollConfig.trySetDefault`（`pkg/cc/types.go:2147`） | `3s × 60 = 180s` |
| `operateProcess` step 超时 | `ProcessOperateSteps.trySetDefault`（`pkg/cc/types.go:2059`） | `3m = 180s` |

于是 GSE 按 600 秒执行，BSCP 在第 180 秒就放弃了。两个值必须**同时**放大：只放大 step，会先被轮询的 60 次上限掐断；只放大轮询次数，会先被 step 的 3 分钟 context 掐断。

轮询与 step 超时的强制关系分别在这两处：

```go
// internal/task/executor/common/common.go:262-277
if inProgressCount >= e.TaskConf.ProcessPoll.MaxRetries {
    return task.ErrEndLoop        // 放弃等待，把 errorCode=115 返回上层
}
...
}, task.LoopInterval(e.TaskConf.ProcessPoll.PollInterval))
```

```go
// bcs-common/common/task/manager.go:377, 432
stepCtx, stepCancel := GetTimeOutCtx(context.Background(), step.MaxExecutionSeconds)
...
case <-stepCtx.Done():
    stepErr := fmt.Errorf("step exec timeout")
```

## 2. 目标与范围

### 目标

普通进程启停任务能容纳单次操作耗时 600 秒（CMDB `op_timeout` 的实际配置量级），并留出合理余量，不再出现"进程已生效但任务判失败"。

### 在范围内

- `taskFramework.processPoll`（GSE 结果轮询上限，全局）
- `taskFramework.processOperate.operateProcess`（普通启停任务中唯一的慢步骤）

### 明确不在范围内

- **更新托管任务**（`processUpdateRegister`）：它内部把 stop → register → start 串成三个步骤，且默认 `maxRetries=3`，放大后最坏时长会成倍增长，需要单独评估。本次不动，保持 3 分钟默认值。
- 代码改造（如按进程 `op_timeout` 动态计算预算、把 worker 数做成可配置）。
- 前端对"任务运行中"的展示与中间态释放逻辑。

### 为什么只改 `operateProcess` 就够

普通启停任务共 6 个步骤，只有第 5 步在等 GSE 真正执行启停，其余都是查库、调 CMDB 或走 `OpTypeQuery` 的秒级查询：

| # | 步骤 | 行为 | 是否需要放大 |
|---|---|---|---|
| 1 | `validateOperateProcess` | 查库校验操作合法性 | 否 |
| 2 | `compareWithCMDBProcessInfo` | 调 CMDB 对比进程配置 | 否 |
| 3 | `compareWithGSEProcessStatus` | GSE 查询（`OpTypeQuery`） | 否 |
| 4 | `compareWithGSEProcessConfig` | 空实现（TODO） | 否 |
| 5 | **`operateProcess`** | **下发启停并等 GSE 执行** | **是** |
| 6 | `finalizeOperateProcess` | GSE 查询 + 写库 | 否 |

启动/停止/强制停止/重启/重载/托管/取消托管这 7 种操作类型**全部复用第 5 步**，操作类型只是任务负载里的一个字段（见 `internal/task/builder/process/process.go:147-157`）。所以一个 `operateProcess` 配置项覆盖全部日常启停场景。

## 3. 取值推导

以 CMDB `op_timeout = 600s` 为基准逐层外推，并**刻意让轮询预算先到期**——这样超时会报「GSE 仍在执行中（errorCode=115）」这种有信息量的错误，而不是被框架无脑掐断成 `step exec timeout`，便于区分"GSE 慢"和"BSCP 卡"。

| 层 | 取值 | 余量来源 |
|---|---|---|
| GSE Agent 执行 | 600s | CMDB `op_timeout`，权威输入 |
| BSCP 轮询上限 | `3s × 260 = 780s` | 比 600s 多 180s，留给 GSE 任务排队与结果落地 |
| `operateProcess` step 超时 | `15m = 900s` | 比 780s 多 120s，留给下发请求、写库、CMDB 调用等 step 内其它 IO |

`pollInterval` 保持 3 秒不变。它与"能否撑住 10 分钟"无关，只影响对 GSE 结果查询接口的压力；当前批量规模为几个到几十个进程实例，远低于 200 的 worker 上限，无需为此调整。

`operateProcess` 的 `maxRetries` 保持默认值 0（不重试），因此该步骤最坏时长就是一份 900 秒预算，不存在重试叠加。

## 4. 配置

追加到 `bk-bscp.yaml` 的 `taskFramework` 段：

```yaml
taskFramework:
  processPoll:
    # 轮询 GSE 进程操作结果：3s × 260 = 780s，需大于 CMDB op_timeout(600s) 并留排队余量
    pollInterval: 3s     # 与默认值相同，显式写出便于对照理解
    maxRetries: 260      # 从默认 60 放大
  processOperate:
    operateProcess:
      # 普通启停任务中唯一等待 GSE 执行的步骤，需大于上面的轮询预算(780s)
      maxExecution: 15m  # 从默认 3m 放大
```

实际只有 `maxRetries` 和 `maxExecution` 两个值发生变化。其余步骤不出现在配置里，由 `trySetDefault` 保持各自的 3 分钟默认值。

### 两个配置陷阱

**一、`maxRetries: 0` 写不进去。** `trySetStepDefault` 用「值为 0」判断「未配置」：

```go
// pkg/cc/types.go:2201-2209
func trySetStepDefault(s *StepTiming, maxExecution time.Duration, maxRetries uint32) {
	if s.MaxExecution == 0 {
		s.MaxExecution = maxExecution
	}
	if s.MaxRetries == 0 {
		s.MaxRetries = maxRetries
	}
}
```

对默认 `maxRetries=3` 的步骤，在 yaml 里显式写 `maxRetries: 0` 会被重新覆盖回 3，最小只能配到 1。本方案不依赖这个能力（`operateProcess` 默认就是 0），但后续处理更新托管任务时会踩到。

**二、生效需要重启。** `cc.G()` 是启动时加载的全局快照，且 `ProcessExecutor` 构造时把 `TaskConf` 值拷贝了一份（`internal/task/executor/process/process.go:72`），不支持热加载。改完必须重启 data-service。

## 5. 已验证事项

以下均已在本机通过临时探针测试（`GlobalSettings` + `yaml.v3` 实际解析）确认，测试后已删除：

- `maxExecution: 15m`、`pollInterval: 3s` 这类 duration 字符串能被 `gopkg.in/yaml.v3` 正确解析为 `time.Duration`（15m0s / 3s）
- 嵌套路径 `taskFramework.processOperate.operateProcess` 正确绑定；仓库内 `.mock-priority-test/bk-bscp.yaml.orig` 里那段 `taskFramework.syncGseStatus` 路径是错的（结构体要求 `taskFramework.syncGSE.syncGseStatus`），**不可照抄**
- 未写入 yaml 的步骤（如 `finalizeOperateProcess`）保持 3m 默认值，不受影响
- `operateProcess.maxRetries` 不写时保持默认 0
- `TaskFramework.validate()` 通过
- `maxRetries: 0` 被覆盖回 3 的行为已复现

另外确认了两处**不需要**处理的层：

- **任务级 / 任务组级超时未设置**。`buildProcessTask` 未传 `WithTaskMaxExecutionSeconds`，`buildProcessTaskGroup` 未传 `WithGroupMaxExecutionSeconds`，两者均为 0；框架在 `GetDeadlineCtx` 中对 `seconds <= 0` 直接跳过 deadline，因此不会因任务总时长被打断。
- **broker 不会重复投递长任务**。etcd broker 的 running key 虽然只有 60 秒 lease，但有 `KeepAlive` 协程在整个投递期间续租（`brokers/etcd/delivery.go:105-127`），15 分钟的 step 不会被另一个 worker 重复消费。

## 6. 验证方式

1. 在 CMDB 上确认目标 Windows 进程的「操作超时时长」为 600 秒量级
2. 改配置并重启 data-service
3. 对该进程执行一次停止，观察日志中轮询在继续而非提前放弃：
   ```
   WaitTaskFinish task <id> in progress, retry=1/260
   WaitTaskFinish task <id> in progress, retry=11/260
   ...
   WaitTaskFinish task <id> finished, errorCode=0, retries=N
   ```
   `retry=N/260` 的分母变成 260 即说明配置已生效
4. 确认任务终态为成功，且进程实例状态与 GSE 实际状态一致
5. 回归一次正常的快进程（Linux，秒级停止）启停，确认耗时没有被拉长——轮询在 GSE 返回非 115 时立即退出，`maxRetries` 只是上限而非固定等待

## 7. 已知风险与残留缺口

这些是配置手段无法覆盖的，需要知情并接受，或另立需求处理。

**风险一：失败路径上的回调等待被同步拉长。** 任务回调跑在 worker 协程里、用 `context.Background()`，完全不受 step 超时约束：

```go
// bcs-common/common/task/state.go:187-191
func (s *State) tryCallback(stepErr error) {
	if s.cbExecutor != nil {
		c := istep.NewContext(context.Background(), GetGlobalStorage(), s.task, s.step)
		if err := s.cbExecutor.Callback(c, stepErr); err != nil {
```

而 `ProcessExecutor.Callback` 内部会调 `getGSEProcessStatus` 再查一次 GSE，共用同一份 `processPoll` 预算。因此回调的最坏阻塞时长从 180 秒变成 780 秒。实际影响有限——回调里走的是秒级返回的 `OpTypeQuery`，只有 GSE 查询接口本身故障时才会触顶。

**风险二：查询类步骤的超时报错变得不易读。** `processPoll` 是全局唯一的旋钮，放大后它（780s）不再先于查询步骤的 step 预算（180s）到期。GSE 查询接口故障时，`compareWithGSEProcessStatus` / `finalizeOperateProcess` 会以 `step exec timeout` 结束，而不是原来那个带 `errorCode=115` 的描述性错误。属于可观测性的轻微退化，不影响正确性。

**风险三：worker 容量。** `defaultWorkerNum = 200` 硬编码在 `internal/task/task.go:50`，无法配置。当前批量规模（几十个）远未触及，但若将来出现上千实例的慢操作批次，会出现明显排队。

**缺口一：中间态没有基于时间的自动释放。** 实例卡在 `starting` / `stopping` 时，所有后续操作都会被 `DisableReasonTaskRunning` 拒绝，判定纯粹基于状态、不看时间（`pkg/protocol/core/process/convert.go:484-488`）。

**缺口二：重启导致状态卡死的暴露窗口变长。** data-service 在慢任务执行中重启时，实例可能停在中间态。这个窗口从原来的最长 3 分钟拉长到 15 分钟。

## 8. 后续可选项

不属于本次交付，按需另立需求。

1. **更新托管任务的超时**：需同时决策 `stopProcess` / `registerProcess` / `startProcess` 的预算与重试次数。注意 `stopProcess` 在同一份 step 预算内串了两次 GSE 等待（先 `queryGSEProcessStatus` 再 `executeGSEOperate`，见 `internal/task/executor/process/update_register.go:211-229`），且默认 `maxRetries=3` 会让最坏时长变成 4 倍。
2. **按进程动态计算预算**：`resolvedInstance.proc` 在下发任务时已持有 `*table.Process`，`Spec.SourceData` 里就有 `Timeout`，把每进程预算传进 step 构建过程不需要额外查库。这样快进程仍能快速失败，不必陪着慢进程一起等。
3. **中间态超时兜底**：给中间态加上基于 `status_updated_at` 的过期判定，避免实例被永久冻结。
4. **worker 数可配置化**：把 `defaultWorkerNum` 提到 `taskFramework` 配置里。
