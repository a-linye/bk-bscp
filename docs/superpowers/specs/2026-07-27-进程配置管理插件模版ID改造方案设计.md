# 进程配置管理插件替换模版名称为模版 ID 方案设计

> 关联需求：1020451610136505423（进程配置管理插件替换模版名称为模版ID，短 ID 136505423）
> 涉及仓库：`bk-bscp`（服务端）、`plugins/bscp-proc-cfg`（bk-sops 标准插件，独立 git 仓库）

## 1. 目标与约束

### 1.1 目标

进程配置管理插件的配置类操作（生成配置、下发配置、检查配置）改为按**配置模版 ID** 指定操作
范围，不再使用模版名称。模版名称虽然在业务内唯一，但可以被删除后重建：重建后的模版是一条新
记录，沿用名称会让存量流程静默作用到一个「同名但不同」的模版上。ID 不可复用，能杜绝这类误操作。

### 1.2 需求澄清阶段已锁定的决策

| 项 | 决策 |
|----|------|
| 改造方式 | 硬替换。插件 v100 原地把字段换成 `config_template_ids`，服务端同步下线名称分支，不保留双写或兼容字段 |
| 存量流程 | 不做特殊检测与兜底，由产品侧通知使用方重填参数 |
| 空值语义 | 「不指定配置模版 = 操作全部配置模版」的语义保留，但受必填校验开关控制 |
| 必填校验开关 | 插件侧环境变量 `BSCP_REQUIRE_CONFIG_TEMPLATE_IDS`，**默认开启**。开启时 ids 为空直接报错，显式关闭后恢复「空 = 全量」。首次上线保持开启，用于拦住存量流程误发全量 |
| ID 语义 | `config_template` 表主键，即 `/config_template/list` 返回项的顶层 `id` |
| 表单交互 | 下拉 label 显示模版名称、value 为 ID；去掉 `allowCreate`，只能从远程数据源选 |
| 缺失 ID 行为 | 批量查询后比对，缺失则报 `RecordNotFound` 并列出全部缺失 ID，任务不发起 |
| proto 处置 | 删除 `config_template_names` 字段并 reserved 编号与字段名 |
| 输入解析 | 保留宽松反序列化，接受 `[1,2]` / `["1","2"]` / `"1,2"`，非数字项报错 |
| 不在本期 | 任务历史页把模版 ID 回显为名称；`release` 动作同步阻塞轮询的异步化重构 |

### 1.3 现状事实基准

服务端的按 ID 链路已存在，本次是收尾而非新建：

- `pkg/protocol/core/process/process.proto` 的 `OperateRange` 已同时有 `config_template_ids`
  （编号 7）与 `config_template_names`（编号 8）。
- `cmd/data-service/service/config_instance.go` 的 `buildConfigTemplateGroups` 已是「有 ids 走
  ids → 否则走 names → 否则全量」三段逻辑，ids 分支注释标注为「预留」。该函数被 `GenerateConfig`
  与配置检查两个入口共用，配置下发复用 `GenerateConfig` 产生的批任务，因此三个配置动作一次覆盖。
- `pkg/dal/table/task_batch.go` 落库的本来就是 `ConfigTemplateIDs`，任务记录侧无需改动。
- 插件侧完全走名称：`Inputs.ConfigTemplateNames`、`form.json` 的 `config_template_names`
  多选下拉（`allowCreate: true`）、`controllers/config_template.go` 把 `spec.template_name`
  同时当 label 与 value（模版的 `id` 已解析但被丢弃）。
- 全仓 `config_template_names` 的唯一生产者是本插件，唯一消费者是 `buildConfigTemplateGroups`，
  其余命中均为 `process.pb.go` 与 `docs/swagger/` 生成物，无第三方调用面。

## 2. 契约变更

插件 → BSCP 的请求体中：

```diff
 "operate_range": {
   "environment": "1",
   "expression_scope": { "set_name": "*", "...": "*" },
-  "config_template_names": ["nginx.conf", "app.yaml"]
+  "config_template_ids": [12, 34]
 }
```

- ID 为 `config_template` 表主键，与 `/config_template/list` 响应里的顶层 `id` 一致，
  **不是** `attachment.template_id`（后者是关联的 template 表 ID）。
- `config_template_ids` 缺省或为空数组时，服务端语义仍为「操作业务下全部配置模版」；这类空值
  请求是否允许发出，由插件侧的必填校验开关决定（见 §3.5）。
- 生效动作：`generate`、`release`、`diffcfg`。进程类动作（start/stop/restart/reload/kill/
  register/unregister）虽然也携带 `operate_range`，但服务端进程路径不消费模版字段，行为不变。

## 3. 插件侧改造（`plugins/bscp-proc-cfg`）

### 3.1 `pkg/types/types.go`

`OperateRange.ConfigTemplateNames []string`（tag `config_template_names`，无 `omitempty`）
替换为 `ConfigTemplateIDs []uint32`（tag `config_template_ids,omitempty`）。补 `omitempty`
同时修掉当前每次请求都发送 `"config_template_names": null` 的问题。

### 3.2 `versions/v100/plugin.go`

- `Inputs.ConfigTemplateNames ConfigTemplateNames` → `ConfigTemplateIDs ConfigTemplateIDs`，
  JSON key 为 `config_template_ids`。
- 自定义类型 `ConfigTemplateNames []string` → `ConfigTemplateIDs []uint32`，`UnmarshalJSON`
  依次尝试：数字数组 `[1,2]` → 字符串数组 `["1","2"]` → 逗号分隔串 `"1,2"`，统一转 `uint32`；
  出现无法解析为正整数的项时返回明确错误。保留宽松解析的理由不是兼容旧名称，而是 bkui-form
  与 bk-sops 全局变量注入回传的参数类型不确定（数字/字符串/模板串）。
- `buildOperateRange` 中原本的「去空格 + 过滤空串」改为「去重 + 过滤 0」。

### 3.3 `controllers/config_template.go`

`ConfigTemplateOption.Value` 从 `string` 改为 `uint32`，`Label` 仍取 `spec.template_name`；
遍历时跳过 `id == 0` 或名称为空的脏数据。返回信封（`{result,code,message,data}`）与路由不变。

### 3.4 `versions/v100/form.json`

- 字段 `config_template_names` 重命名为 `config_template_ids`，同步修改 `ui:order` 以及
  `job_action_choices` 那条控制显隐的 `ui:reactions`（`target` 名与 else 分支的 `value: []`）。
- `items.type` 由 `string` 改为 `number`。
- 移除 `ui:component.props.allowCreate`（手输 ID 无意义且易错）。
- `remoteConfig` 的 url、method、params 不变，仅返回的 value 由名称变为数字 ID。
- `ui:props.desc` 维持「不指定时默认操作全部配置」，不提必填校验开关：开关是部署侧的实现细节，
  不该出现在使用者看到的表单说明里。
- 字段仍不在 JSON Schema 的 `required` 中，理由见 §3.5。

### 3.5 必填校验开关

新增环境变量 `BSCP_REQUIRE_CONFIG_TEMPLATE_IDS`，**默认开启**：取值为 `false` 或 `0` 时关闭，
其余情况（含未配置、空串、无法识别的值）一律开启。沿用 `BSCP_DEBUG` 的字符串直接比较风格，不引
入额外的配置解析。变量由蓝鲸开发者中心注入，不需要在 `app_desc.yml` 声明。

开关开启时，`validateInputs` 在配置类动作（`generate`/`release`/`diffcfg`）下要求
`ConfigTemplateIDs` 非空，为空则直接返回错误，不发起任何请求；进程类动作与 `sync_status`
不受影响。关闭后恢复「空 = 操作全部配置模版」。

作用是给存量流程兜底：插件发布后，存量流程保存的仍是 `config_template_names`，新字段解析为空，
若无此开关会静默命中服务端的「全量」分支。开关开启后这类流程会明确失败，等使用方重填参数、
确认无遗漏后再决定是否关闭。

`form.json` 是静态文件、读不到环境变量，因此表单层面无法把字段标成必填。开关开启时用户仍可在
页面上保存空值，执行阶段才失败。错误信息需要写清楚是环境策略要求必选，而不是让人以为字段本身
坏了。

## 4. 服务端改造（`bk-bscp`）

服务端不引入这个开关。bk-bscp 的配置统一走 `bk-bscp.yaml`，为一个临时性的过渡策略引入环境变量
与其模式不符；且 `config_template_ids` 的唯一生产者就是本插件，插件侧拦截已经覆盖全部来源。

### 4.1 proto 与生成物

`pkg/protocol/core/process/process.proto` 删除 `repeated string config_template_names = 8`，
把编号 8 与字段名并入既有的 reserved 声明（与 2-6 的处理方式一致）：

```protobuf
reserved 2, 3, 4, 5, 6, 8;
reserved "set_name", "module_name", "service_name", "process_alias", "cc_process_id",
    "config_template_names";
```

随后执行 `make pb` 重新生成 `process.pb.go`，`make api_docs` 与 `make bkapigw_docs` 更新
`docs/swagger/` 下的 4 个 swagger 文件（当前均含该字段）。

### 4.2 DAO

`internal/dal/dao/config_template.go` 的接口与实现各新增 `ListByIDs`，仿照现有 `ListByNames`：

```go
// ListByIDs list config templates by ids.
ListByIDs(kit *kit.Kit, bizID uint32, ids []uint32) ([]*table.ConfigTemplate, error)
```

实现为 `Where(m.BizID.Eq(bizID), m.ID.In(ids...)).Find()`，保持业务隔离。

### 4.3 `cmd/data-service/service/config_instance.go`

- `buildConfigTemplateGroups` 的三段分支收敛为两段：`len(ids) > 0` 走 ID 查询，否则全量；
  删除 `else if len(names) > 0` 分支。
- `getConfigTemplatesByIDs` 从「对每个 ID 调一次 `GetByID`」改为「去重 → 一次 `ListByIDs` →
  比对缺失 → 缺失则 `errf.RecordNotFound` 并列出全部缺失 ID」。当前实现是 N 次查询，且模版被
  删时 `Take()` 的 record-not-found 被统一包成 `DBOpFailed`，错误码与提示都不准确。
- 删除不再被引用的 `getConfigTemplatesByNames`。
- 修正两行缺格式化占位符的调试日志：`logs.Infof("buildConfigTemplateGroups",
  configTemplateGroups)` 与 `logs.Infof("pluginMode", pluginMode)`。

### 4.4 i18n

新增 key `config templates not found for ids: %v`；旧的 names key 随分支删除。操作流程：
执行 `make i18n` 让 gotext 提取新 key → 在 `internal/i18n/translations/locales/zh/
messages.gotext.json` 对应条目的 `translation` 字段补中文（参照现有「以下名称的配置模板未找到」
的写法）→ 再执行一次 `make i18n` 使 `catalog.go` 带上翻译。

## 5. 数据流

1. bk-sops 表单初始化 → `$loadDataSource()` 请求插件 `/bk_plugin/plugin_api/list_config_template`
   → 插件调 BSCP `/config_template/list` → 返回 `[{label: 模版名称, value: 模版ID}]`。
2. 用户多选，流程模板保存 `config_template_ids: [12, 34]`。
3. 插件 `Execute` → `validateInputs`（开关开启时校验 ids 非空）→ `buildOperateRange` 去重过滤
   → 请求 BSCP 生成/检查接口。
4. 服务端 `buildConfigTemplateGroups`：按 `operate_range` 匹配进程 → 按 ID 批量查模版
   （缺失即报错）→ 查各模版最新版本 → 组装 `ConfigTemplateGroup` → 发起批任务。
5. 插件轮询 `task_batch/{id}/detail` 直至终态。

## 6. 错误处理

| 场景 | 行为 |
|------|------|
| ids 为空 + 开关开启（默认） | 插件 `validateInputs` 报错，不发请求 |
| ids 为空 + 开关显式关闭 | 操作业务下全部配置模版 |
| 存在已删除的模版 ID | `RecordNotFound`，错误信息列出全部缺失 ID，任务不发起 |
| ID 无法解析为正整数 | 插件在 `ReadInputs` 阶段报错，不发请求 |
| ID 属于其它业务 | DAO 带 `biz_id` 条件，查不到，等同缺失 ID 报错 |
| 表达式命中进程为空 | 沿用现有 `RecordNotFound`，不降级为全选 |

## 7. 发布顺序与风险

**插件先发布（开关保持默认开启），服务端后发布。** 若顺序颠倒，服务端一删名称分支，所有仍在传
名称的存量流程会立刻从「按名称下发」退化为「全量下发」。按此顺序，中间窗口里插件传的 ids 优先
生效，行为始终正确，且服务端保留名称分支期间不会被任何调用方触发。

发布后的收尾节奏：通知使用方把流程里的配置模版重新选一遍 → 确认没有流程还依赖旧参数 → 再按需
决定是否关闭开关恢复「不指定 = 全量」的便利用法。

已知并接受的风险：

1. **存量流程会失败而不是静默全量。** 插件发布后，流程模板里保存的 `config_template_names`
   会被反序列化忽略，`config_template_ids` 为空。开关默认开启，因此这类流程明确报错、任务不发起
   ——这是刻意选择的失败方式，代价是使用方必须重填参数后才能恢复执行。
2. **开关关闭后风险回归。** 一旦显式关闭开关，空 ids 会重新命中「全量」分支。关闭前必须确认
   所有存量流程都已重填参数。
3. **proto 删字段为破坏性变更。** 已确认全仓无其它生产者/消费者；若存在仓外调用方直接拼
   `operate_range.config_template_names`，该字段将被忽略，且不受插件侧开关保护，会退化为全量。

## 8. 测试策略

插件侧单元测试（`versions/v100/plugin_test.go`、`pkg/types/types_test.go`）：

- `ConfigTemplateIDs.UnmarshalJSON` 覆盖数字数组、字符串数组、逗号串、非法项报错、空值。
- `buildOperateRange` 覆盖去重、过滤 0、空输入不产生 `config_template_ids` 字段。
- `ListConfigTemplate` 覆盖 value 为数字 ID、脏数据被跳过、异常时仍返回空数组信封。
- `validateInputs` 覆盖开关矩阵：默认（未配置）空 ids 报错、显式 `false`/`0` 空 ids 放行、
  开关开启但动作为进程类或 `sync_status` 时不校验。开关读取环境变量，测试需用 `t.Setenv`。

服务端单元测试：

- `getConfigTemplatesByIDs`：去重、缺失 ID 报 `RecordNotFound` 且信息含全部缺失 ID。
- `buildConfigTemplateGroups`：空 ids 走全量分支；指定 ids 只组装对应模版组。

集成与人工验证：

- 用 bk-plugin-develop-skill 的 `simulate_invoke.py` 做 local protocol simulation，校验
  `/bk_plugin/invoke/v100` 的 payload 与 `/bk_plugin/detail/v100` 的表单结构。**这是本地协议
  模拟，不等价于真实 BK-SOPS 执行。**
- 在 bk-sops 页面人工验证一次：下拉能正常加载、多选回显正确、保存后再次打开参数不丢失、
  三个配置动作端到端跑通、指定一个已删除模版 ID 时报错信息清晰。
- 用一个仍保存着 `config_template_names` 的存量流程验证开关：开关开启时执行失败且提示可读，
  关闭开关后退化为全量下发。
