# 执行与验证（Execution & Verification）

> 目标：每个任务都以可观察状态开始，以与风险匹配的新验证证据结束。

## 1. Agent Loop

```text
观察：确认需求、工作区、现有实现、测试和约束
  ↓
计划：拆分最小可验证步骤，识别风险与用户决策点
  ↓
行动：在授权范围内执行一个边界清晰的步骤
  ↓
验证：检查文件、诊断、测试、构建或外部目标状态
  ↓
更新：记录完成项、证据、剩余风险；未通过则修复后重验
```

### 1.1 循环保护

| 机制 | 默认值 | 触发动作 |
|------|-------|---------|
| 最大循环次数 | 20 次 | 暂停并汇总当前证据与剩余问题 |
| 单任务最大执行时间 | 30 分钟；长构建单独估时 | 报告进度并请求是否继续 |
| 无进展检测 | 连续 3 次状态无实质变化 | 停止重复操作，重新诊断或请求决策 |
| 自动修复次数 | 同一根因最多 3 次 | 保留失败证据并升级人工处理 |
| 范围检查 | 每完成一个子任务 | 对照需求与改动文件，移除任务外动作 |

这些默认值不用于中断已明确要求持续监控的任务；监控任务以健康状态或用户停止为终点。

## 2. 开始前检查

1. 明确请求属于回答、诊断、设计、实现、评审、提交还是外部系统操作。
2. 读取 `git status --short`，识别用户已有改动和当前任务允许修改的路径。
3. 从需求/Spec 列出可验收结果；行为变更先确定测试方式。
4. 加载涉及端的技术规范、安全规范和架构约束。
5. 探测必需工具与权限；缺失时只报告会阻塞当前场景的依赖。

## 3. 分层验证

### 3.1 Go

| 变更 | 最小验证 | 扩展验证 |
|------|---------|---------|
| 单包逻辑 | `gofmt` + `go test ./path/to/package` | 相关调用方包测试 |
| 跨包/公共类型 | 受影响包测试 | `go test ./...` 或相关服务构建 |
| 服务装配/入口 | 对应包测试 | `make build_bscp` |
| Linter 相关 | IDE 诊断或目标 linter | CI 等价的 golangci-lint |
| 模块依赖 | `go mod tidy` 后检查 diff | CI `go-tidy-check` |

不要只运行全量编译替代有针对性的行为测试。修改 Go 文件必须运行 `gofmt`。

### 3.2 前端

在 `ui/` 下执行：

| 变更 | 验证 |
|------|------|
| TypeScript/Vue 逻辑 | 对应测试（存在时）+ `npm run lint` |
| 类型、组件或构建配置 | `npm run build` |
| 格式化 | 仅格式化受影响文件，检查无无关 diff |

涉及交互行为时补充人工验收步骤；不能仅凭构建通过宣称用户路径正确。

### 3.3 协议与生成物

1. 修改权威 `.proto` 或生成器，不直接编辑 `*.pb.go`、`*.pb.gw.go` 等生成文件。
2. 按影响运行 `make pb api_docs bkapigw_docs normalize_proto_docs`。
3. 检查生成 diff 仅包含预期接口变化。
4. 运行相关服务测试/构建；CI 会再次执行生成物一致性检查。

### 3.4 数据库与任务

- 迁移需覆盖已有数据、空数据、重复执行和失败恢复/前向修复。
- 定时任务、消息和发布链路需验证幂等、重试、超时、重复/乱序输入。
- 数据修复脚本先提供只读统计或 dry-run；生产执行需单独授权。

### 3.5 文档与 Harness

- 验证引用路径、标题锚点、命令和版本与权威源一致。
- Harness 变更运行十项完整性检查；代码提交后运行文档园艺轻量模式。
- `docs/standards/` 与预设逐字一致；`docs/dev-map/` 在代码结构变化后更新。

## 4. 预完成清单

| 检查项 | 证据 | 跳过条件 |
|-------|------|---------|
| 需求/Spec 逐条满足 | 验收项与实现对应关系 | 无 |
| 工作区范围正确 | `git status --short`、`git diff` | 无 |
| 格式正确 | `gofmt` / 前端格式检查 | 无对应代码 |
| 目标测试通过 | 新鲜测试输出 | 无行为或测试影响 |
| 构建通过 | 新鲜构建输出 | 无构建影响 |
| 无新增诊断 | Linter/IDE 诊断 | 无代码影响 |
| 生成物同步 | 生成命令 + diff | 无生成源影响 |
| 文档同步 | 受影响文档检查 | 无文档影响 |
| 安全与架构检查 | 规范清单/评审结果 | 无代码影响 |

失败后先定位根因再修复；不得通过跳过测试、关闭规则或扩大忽略范围伪造通过。

## 5. 漂移检测

| 信号 | 处理 |
|------|------|
| 修改需求外文件 | 停止并确认来源；不回滚用户改动 |
| 顺手重构或引入新抽象 | 删除或拆出独立提案 |
| 未经确认改变协议/数据库/架构方案 | 暂停并请求用户决策 |
| 重复运行同一失败命令 | 转入系统化诊断，检查根因假设 |
| 依赖安装或生成产生大范围 diff | 核对锁文件、版本和生成入口 |
| 外部系统状态与预期不符 | 读取当前状态，不继续连锁写操作 |

## 6. 可观测记录

执行报告至少包含：

- 任务目标与实际变更路径；
- 关键决策及其来源；
- 运行的测试、构建、Linter 和生成命令及结果；
- 未执行验证及原因；
- 环境缺口、剩余风险和人工验收步骤；
- 外部写操作的目标标识和写后验证结果。

`tapd-story-pipeline` 的阶段日志与状态文件是需求实现流程的主要审计来源；普通任务使用会话工具记录和 Git diff，不额外提交临时日志。

## 检查清单

- [ ] 开始前已确认任务模式、工作区和验收标准
- [ ] 每个行动后都有对应观察或验证
- [ ] 测试和构建范围与风险匹配
- [ ] 未通过绕过规则、扩大忽略或删除测试制造成功
- [ ] 完成结论包含新鲜证据和未验证项
- [ ] 改动范围未漂移，用户已有改动未受影响
