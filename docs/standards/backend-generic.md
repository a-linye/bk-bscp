## 二、项目结构

```
{project}/
├── api/                     # 接口定义
├── cmd/                     # 服务入口
├── configs/                 # 配置文件
├── internal/                # 内部业务逻辑
│   └── {module}/
│       ├── handler.go       # 请求处理
│       └── service.go       # 业务逻辑
├── pkg/                     # 公共库
├── scripts/                 # 构建脚本
└── deploy/                  # 部署配置
```

### 目录职责原则

- `api/`：接口定义是唯一事实源，对外暴露契约
- `internal/`：内部实现，不对外暴露
- `pkg/`：通用工具库，可跨项目复用
- `cmd/`：程序入口，负责依赖注入和服务启动

## 三、接口定义规范

### 3.1 通用原则

- 接口定义先于实现（Contract First）
- 接口定义文件纳入版本控制
- 自动生成的代码禁止手动修改

### 3.2 命名约定

| 元素 | 规则 | 示例 |
|------|------|------|
| Service | PascalCase + "Service" | `UserService` |
| 方法 | PascalCase: `{Action}{Resource}` | `CreateUser` |
| 字段 | snake_case | `user_id`, `created_at` |

### 3.3 版本兼容性规则

| 规则 | 说明 |
|------|------|
| 禁止删除已发布字段 | 标记废弃代替删除 |
| 禁止修改字段标识 | 一旦分配不可变更 |
| 新字段向后兼容 | 使用可选标记 |

## 四、分层架构

### 4.1 三层设计

```
┌─────────────────────────────────────┐
│  Handler 层（请求处理）              │
│  - 接收请求                          │
│  - 参数校验                          │
│  - 调用 Service 层                   │
│  - 返回响应                          │
├─────────────────────────────────────┤
│  Service 层（业务逻辑）              │
│  - 核心业务逻辑                      │
│  - 事务管理                          │
│  - 调用 Repository 层               │
├─────────────────────────────────────┤
│  Repository 层（数据访问）            │
│  - 数据库 CRUD                       │
│  - 缓存操作                          │
│  - 外部服务调用                      │
└─────────────────────────────────────┘
```

### 4.2 依赖规则

| 层 | 允许依赖 | 禁止依赖 |
|----|---------|---------|
| Handler | Service, 接口定义 | Repository, 数据库包 |
| Service | Repository, 其他 Service | 数据库包直接操作 |
| Repository | 数据库驱动, ORM | 其他 Service |

## 五、编码规范

### 5.1 通用原则

- 函数/方法职责单一
- 错误必须显式处理，禁止忽略
- 使用依赖注入，便于测试
- 接口优于具体类型（依赖倒置）

## 六、错误处理

### 6.1 错误定义原则

- 定义业务错误类型，区别于系统错误
- 错误信息对用户友好
- 错误传播时保留原始上下文

### 6.2 错误传播规则

| 规则 | 说明 |
|------|------|
| 包装错误 | 添加上下文信息后传播 |
| 不隐藏错误 | 禁止忽略错误返回值 |
| 用户友好 | Handler 层转换为用户可读消息 |
| 日志记录 | Service 层记录，Handler 层不重复 |

## 八、日志规范

### 8.1 日志级别

| 级别 | 使用场景 |
|------|---------|
| DEBUG | 开发调试，生产关闭 |
| INFO | 正常业务流程 |
| WARN | 非预期但可恢复 |
| ERROR | 错误但服务可运行 |
| FATAL | 不可恢复，服务退出 |

### 8.2 日志规则

| 规则 | 说明 |
|------|------|
| 结构化日志 | 使用字段而非字符串拼接 |
| 禁止敏感信息 | 密码、Token 不得出现在日志中 |
| 请求追踪 | 包含 request_id、方法名、耗时 |
| 错误链完整 | 包含完整错误上下文 |
| 避免高频日志 | 循环内不打 INFO |

## 九、测试规范

### 9.1 测试分类

| 类型 | 覆盖层 | 说明 |
|------|--------|------|
| 单元测试 | Service, Utils | 快速、隔离 |
| 集成测试 | Handler + 外部依赖 | 验证集成正确性 |
| E2E 测试 | 完整 API | 端到端验证 |

### 9.2 Mock 策略

| 依赖 | Mock 方式 |
|------|----------|
| 数据库 | Interface + Mock 实现 |
| 外部服务 | Mock Server |
| 时间 | 注入 Clock 接口 |
| 配置 | 测试专用配置 |

### 9.3 覆盖率要求

| 层 | 最低覆盖率 |
|----|-----------|
| Service 层 | ≥ 80% |
| Utils/Pkg | ≥ 90% |
| Handler 层 | ≥ 60% |

## 十、安全规范

| 规则 | 说明 |
|------|------|
| 加密通信 | 服务间通信使用 TLS |
| 认证鉴权 | 所有 API 必须经过认证 |
| 输入校验 | 所有外部输入必须校验 |
| 注入防护 | 使用参数化查询 |
| 敏感数据 | 日志、响应中不暴露 |
| 依赖安全 | 定期扫描漏洞 |

## 十二、服务注册与通信

### 12.1 通用原则

- 服务注册与发现机制明确
- 服务间调用配置超时、重试、熔断
- 生产环境通信必须加密

### 12.2 异步任务

| 适用场景 | 说明 |
|---------|------|
| 耗时操作 | 超过 30 秒的操作 |
| 多步骤流程 | 需要编排的复杂流程 |
| 需要重试 | 可能失败的操作 |
| 状态追踪 | 需要展示进度的操作 |
